### 硬前置：维护窗口内的连接纪律

步骤 4-7 期间 `patra_catalog` / `patra_catalog_v05_backup` 必须**零外部连接**，否则
`ALTER DATABASE ... RENAME` 会报 `is being accessed by other users`。因此窗口内：

- **MacBook 上不允许运行任何 catalog 进程**——IDEA 里的 catalog dev profile 直连 `mini:15432`，
  是本手册最容易被忽略的连接来源。开工前先把本地 catalog / 相关 IT 全停掉。
- 不要在窗口内开 psql 交互会话连这两个库（`\c` 到 `postgres` 库操作）。
- 步骤 5 的原子块用 `ALLOW_CONNECTIONS false` + `pg_terminate_backend` 把窗口关死，
  不依赖"人都记得停"，但纪律仍是第一道闸。

### 关键约定

1. **CD 隔离必须早于合并 PR**（步骤 2 → 步骤 3）。顺序反了，CD 会把新镜像推上 mini 对着旧库启动，
   Flyway `validateOnMigrate` 因 V3 checksum 变化直接失败，catalog 起不来。
2. `generation` 只是 Spring Batch 的 identifying 参数，**只解除 JobInstance 复用限制**，
   只在空库上才有"重导"效果；它**不改变 `importBatch` 的值**——重建后数据行仍标 baseline 批次，
   **验收 SQL 一律不要按代次筛数据**。
3. attempt 规则：同一新库导入失败后续跑 → **沿用同一 `generation`**（利用断点续传）；
   回滚后从空库重来 → **必须换新 generation**（如 `v0.6-attempt2`），否则会从旧 checkpoint 续跑，
   造成前半段数据缺失。
4. 参考基线数字（v0.5 旧库，2026-08-29 实测）：`cat_publication` 18,807 行、
   `cat_publication_abstract` 5,114 行、`cat_publication_author` **0** 行（本版才实现）、
   `cat_venue` 15,434、`cat_organization` 120,445、`cat_venue_publication_stats` 296,600。
   历史 Job 计数：read=30,000 / write=18,815 / filter=11,185。
5. 各步失败后能否原地重跑，见 **附录 B：断点续做表**。

## 步骤 1：物理备份保险

`rename` 只是同 volume 的回滚锚，这份 dump 是独立于 volume 的保险，**直接落宿主**
（不经容器 `/tmp`，少一次拷贝、少一个失效点）。

```bash
ssh mini '
  set -e
  # docker exec 不加 -t（加了会污染二进制流）；stdout 直接重定向到宿主文件
  docker exec patra-postgres pg_dump -U postgres -d patra_catalog -Fc \
    > ~/patra_catalog_v05_full.dump
  ls -lh ~/patra_catalog_v05_full.dump
  shasum -a 256 ~/patra_catalog_v05_full.dump
'
# 预期: 文件大小数百 MB ~ 数 G；sha256 记进执行记录（回滚兜底时要对照）

# 归档可读性验证（把宿主文件挂进容器读，避免再拷一份）
ssh mini '
  docker cp ~/patra_catalog_v05_full.dump patra-postgres:/tmp/verify.dump
  docker exec patra-postgres pg_restore --list /tmp/verify.dump | head -20
  docker exec patra-postgres sh -c "sha256sum /tmp/verify.dump"
  docker exec patra-postgres rm -f /tmp/verify.dump
'
# 预期: --list 能列出条目（归档可读）；容器内 sha256 与宿主 shasum 完全一致
```

**失败处理**：`pg_restore --list` 报错 = 归档不可读 → 重做备份；
两侧 sha256 不一致 = 传输损坏 → 重做备份。备份不可读绝不允许进入步骤 4。

## 步骤 5：换库（建立回滚锚）

**关门 → 踢连接 → 改名，一次 psql 调用内完成**，中间不给新连接留窗口。

```bash
# 注意 docker exec **必须带 -i**：heredoc 走 stdin，不加 -i 的话 psql 读到的是空输入
ssh mini "docker exec -i patra-postgres psql -U postgres -d postgres -v ON_ERROR_STOP=1 <<'SQL'
-- 1) 关门：拒绝一切新连接（此后 IDEA 自动重连也进不来）
ALTER DATABASE patra_catalog WITH ALLOW_CONNECTIONS false;
-- 2) 踢掉存量连接（排除自己）
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
 WHERE datname = 'patra_catalog' AND pid <> pg_backend_pid();
-- 2.5) pg_terminate_backend 是异步的（只发信号，不等后端真正退出）。
--      不等一下，紧接着的 RENAME 有概率仍撞 "is being accessed by other users"。
SELECT pg_sleep(2);
-- 3) 改名为回滚锚
ALTER DATABASE patra_catalog RENAME TO patra_catalog_v05_backup;
-- 4) 新库建出来即先关门，Flyway 之前不接受任何连接
CREATE DATABASE patra_catalog;
ALTER DATABASE patra_catalog WITH ALLOW_CONNECTIONS false;
SQL"

ssh mini "docker exec patra-postgres psql -U postgres -c \"
  SELECT datname, datallowconn FROM pg_database WHERE datname LIKE 'patra_catalog%' ORDER BY 1;\""
# 预期两行:
#   patra_catalog              | f
#   patra_catalog_v05_backup   | f
```

> - `-d postgres` 是必须的：不能连着 `patra_catalog` 去改它自己的名字。
> - `datallowconn=f` 会跟着 rename 一起带到 backup 库上——**这是有意的**（窗口内谁也别连它），
>   步骤 7 的 `pg_dump` 前会临时放开。
> - `ON_ERROR_STOP=1` 保证任一句失败就整体中止，不会出现"关了门没改名"的半截状态。
> - **维护本块 SQL 时的硬约束：heredoc 里不要出现 `$`**。整段被包在 `ssh mini "..."` 的
>   双引号里，任何 `$` 都会**先在 MacBook 本地展开**再发出去。这意味着 PL/pgSQL 的
>   `$$ ... $$` 函数体、`$1` 位置参数、`$tag$` dollar-quoting 都会被本地 shell 吃掉或改写，
>   且失败得很隐蔽（发出去的 SQL 已经不是你写的那段）。当前块只用了纯 SQL 语句，安全；
>   若将来确实需要 `$`，改成先把 SQL 写进 mini 上的 `.sql` 文件再 `psql -f` 执行。

**从此刻起，回滚 = 走文末「回滚流程」。**

**失败处理**：Flyway 报错 / 表数不对 → **不要原地改完重启**，直接走「回滚流程」。

`flyway repair`；而此时新库本来就是空的，丢掉重来（drop + 重新走步骤 5-6）成本远低于 repair，
且能保证 checksum 谱系干净。

### 7.0 allowlist 盲核（不是数个数，是做 diff）

脚本里的 33 张 KEEP 表是 2026-08-29 对线上核对的结果。执行前把线上表清单与

**先确认两侧脚本同版本**——下面的 diff 从 MacBook 本地仓库抽 `TABLES`，而 7.1 执行的是
mini 上 runner workspace 的那份副本。两者不同 commit 的话，diff 通过了但跑的是另一个 allowlist：

```bash

```

两条输出的 commit 必须一致。不一致就先把本地 main 同步好（或重跑步骤 3.2 的 fetch），再往下走。

`information_schema` 必须连进目标库才能查，而 backup 库在步骤 5 被设成 `datallowconn=false`，
所以先临时放开（7.1 跑完再关回去）：


**generation 语义提醒（照抄前务必读）**：

- `generation` 是 identifying job parameter，**唯一作用**是让 `pubmedBaselineImportJob` 在同一 `fileIndex`
  上生成新的 JobInstance，绕开 `JobInstanceAlreadyCompleteException`。
- 它**不改变 `importBatch`**：重建后数据行仍标 baseline 批次（`baseline-pubmed26n1333` 形态），
  **不携带代次信息**。步骤 9 的验收 SQL 因此一律不按代次筛数据。
- 它**只在空库上才有"重导"效果**：对非空库跑同一 generation 是续跑语义，不是重来。
- attempt 规则：
  - 本次导入中途失败、**库不回滚**、要接着跑 → 沿用 `generation=v0.6`（走断点续传）。
  - 走了「回滚流程」、从空库重来 → **换成 `generation=v0.6-attempt2`**（依次递增）。
    沿用旧值会从旧 checkpoint 续跑 → 前半段数据缺失，且验收总行数对不上。
- `authorImportJob` **不需要重跑**：`cat_author` 家族已由步骤 7 回填。

**失败处理**：Job 失败但错在下载层（NCBI 抖动）→ 沿用同 generation 重触发即可。
错在写入层（数据 / schema 问题）→ 走「回滚流程」。

**对账口径：不要求逐项严格相等，但每一项偏差必须落在可解释范围内。**

唯一被认可的偏差来源是**源文件内同一 PMID 出现多次**——Writer 是 first-win（同 PMID 只落一行），
而脚本按 XML 中的出现次数统计。因此：

| 脚本输出 | 应等于 | 允许偏差 |
|---|---|---|
| 基准集文献数(imported_pmids) | `publications` | 0（同一条 SQL 导出的，必须严格相等） |
| 其中在本 XML 中命中 | `publications` | `0 ~ DUP_PMIDS`（步骤 0.6 量出的重复数） |
| 含摘要文献数 | `abstracts` | `0 ~ DUP_PMIDS` |
| 有效作者数 | `pub_authors` | `0 ~ DUP_PMIDS × 单篇作者数`（重复篇的作者被重复计） |
| 含ORCID作者数 | 见 9.3 的 `orcid_normalized` | 差额 = 归一化被拒的非法 ORCID 数，逐项列出 |
| 姓名全空跳过作者数 | 库内无对应行 | 仅记录，不参与对账 |

`DUP_PMIDS=0` 时上述所有偏差都必须为 0。**超出可解释范围的偏差就是缺陷，不要放行。**

### 9.3 ORCID 报告

```sql
SELECT count(*)                                                     AS total_authors,
       count(*) FILTER (WHERE orcid IS NOT NULL)                    AS orcid_normalized,
       count(*) FILTER (WHERE author_id IS NOT NULL)                AS orcid_linked,
       count(*) FILTER (WHERE orcid IS NOT NULL AND author_id IS NULL) AS orcid_unlinked
  FROM cat_publication_author;

-- 归一化形态抽查：应全为 19 位 0000-0000-0000-0000X 形态，无 URL 前缀、无小写 x
SELECT count(*) FROM cat_publication_author
 WHERE orcid IS NOT NULL
   AND orcid !~ '^[0-9]{4}-[0-9]{4}-[0-9]{4}-[0-9]{3}[0-9X]$';      -- 应 0

-- 软关联正确性：命中的 author_id 必须能在 cat_author_orcid 里找到同一 ORCID
SELECT count(*) FROM cat_publication_author pa
  LEFT JOIN cat_author_orcid ao ON ao.author_id = pa.author_id AND ao.orcid = pa.orcid
 WHERE pa.author_id IS NOT NULL AND ao.id IS NULL;                  -- 应 0
```

`orcid_unlinked`（有 ORCID 但 `author_id` 为空）由两部分构成，都属正常，但要分开记录：

1. **`cat_author_orcid` 未收录**：源里有 ORCID，但 `authorImportJob` 导入的作者集里没有这个 ORCID。
   这是主要来源，占比高。
2. **同篇重复 ORCID 被主动置 null**：`uk_pub_author` 是 `(publication_id, author_id)` 的部分唯一索引，
   同一篇里若两个作者行携带同一个已消歧 `author_id`（源数据把同一 ORCID 标在了多个作者上），
   后一个的 `author_id` 会被置 null 以避免违反唯一索引——**作者行本身保留，`orcid` 列也保留**。

分项量出第 2 类。注意口径必须是**行数**（不是"组数"）才能与 `orcid_unlinked` 相减：
一组里有 n 行同 ORCID，只有第 1 行保住 `author_id`，其余 `n-1` 行被置 null。

```sql
SELECT coalesce(sum(c - 1), 0) AS unlinked_by_dup_orcid
  FROM (
    SELECT publication_id, orcid, count(*) AS c
      FROM cat_publication_author
     WHERE orcid IS NOT NULL
     GROUP BY publication_id, orcid
    HAVING count(*) > 1
  ) t;
```

> 这是**上限**而非精确值：只有当那个 ORCID 确实在 `cat_author_orcid` 里命中过、
> 本该填上 `author_id` 时，置 null 才真的贡献了一个 `orcid_unlinked`；
> 若该 ORCID 本来就未收录（第 1 类），这几行无论如何都是 null，会被重复计入两类。
> 因此对账写成 `orcid_unlinked ≤ 未收录数 + unlinked_by_dup_orcid`，能对上即可放行。

## 回滚流程（步骤 5 之后任一步失败时执行）

三库名交换，避免重名冲突。

```bash
# 1. 停 catalog
ssh mini "docker stop patra-catalog || true"

# 2. 关门 → 踢连接 → 三库名交换 → 复位 datallowconn，一次 psql 调用内完成
TS=$(date +%Y%m%d%H%M)   # 在 MacBook 本地展开，下面双引号内的 ${TS} 发出去时已是字面时间戳
ssh mini "docker exec -i patra-postgres psql -U postgres -d postgres -v ON_ERROR_STOP=1 <<'SQL'
ALTER DATABASE patra_catalog WITH ALLOW_CONNECTIONS false;
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
 WHERE datname LIKE 'patra_catalog%' AND pid <> pg_backend_pid();
-- terminate 是异步的，等后端真正退出，否则下面两句 RENAME 可能撞 is being accessed
SELECT pg_sleep(2);
-- 失败库改名带时间戳（留证据，不删）
ALTER DATABASE patra_catalog RENAME TO patra_catalog_v06_failed_${TS};
-- backup 复位为正名
ALTER DATABASE patra_catalog_v05_backup RENAME TO patra_catalog;
-- **必须复位 datallowconn**：步骤 5 把 backup 关了门，不放开的话
-- 库名虽然对了但一切连接仍被拒，表现为"回滚了还是起不来"
ALTER DATABASE patra_catalog WITH ALLOW_CONNECTIONS true;
SQL"

ssh mini "docker exec patra-postgres psql -U postgres -c \
  \"SELECT datname, datallowconn FROM pg_database WHERE datname LIKE 'patra_catalog%' ORDER BY 1;\""
# 预期两行:
#   patra_catalog                    | t     ← 必须是 t
#   patra_catalog_v06_failed_<TS>    | f

# 3. 用步骤 0.3 记录的 OLD_TAG 启动旧镜像
ssh mini "cd /Users/linqibin/Projects/patra/patra-infra/docker && \
  CATALOG_IMAGE_TAG=<OLD_TAG> docker compose -f docker-compose.apps.yaml up -d catalog"

# 4. 验证旧镜像 + 旧库正常
ssh mini "curl -fs http://127.0.0.1:6300/actuator/health"
ssh mini "docker exec patra-postgres psql -U postgres -d patra_catalog -Atc 'SELECT count(*) FROM cat_publication;'"
# 预期: UP + 18807（v0.5 基线）

# 5. 冒烟：经网关取一页（page 从 1 起，@Min(1)；参数名是 pageSize 不是 size）
curl -s --noproxy '*' "http://100.103.73.27:9528/patra-catalog/portal/publications?page=1&pageSize=5" | head -c 400
```

**回滚后再战的三条硬规则**：

1. `patra_catalog_v06_failed_<TS>` **不要立刻删**——排查根因要用。
2. 重新从步骤 4 开始（步骤 1-3 的备份 / CD 隔离 / 镜像仍有效，无需重做）。
3. 步骤 8 的 `generation` **必须换新值**（`v0.6-attempt2`、`v0.6-attempt3` …），
   否则会从旧 checkpoint 续跑，导致前半段数据缺失。

**极端情况**（volume 损坏、backup 库也不可用）：用步骤 1 的宿主物理备份重建：

```bash
# 先把宿主 dump 送回容器，并核对 sha256 与步骤 1 记录值一致
ssh mini '
  set -e
  shasum -a 256 ~/patra_catalog_v05_full.dump          # 与步骤 1 记录值逐字比对
  docker cp ~/patra_catalog_v05_full.dump patra-postgres:/tmp/
  docker exec patra-postgres sh -c "sha256sum /tmp/patra_catalog_v05_full.dump"
'
# 两个 sha256 必须相同，且等于步骤 1 记录值；不一致就别恢复（拷贝损坏）

ssh mini '
  set -e
  docker exec patra-postgres psql -U postgres -d postgres -c "DROP DATABASE IF EXISTS patra_catalog;"
  docker exec patra-postgres psql -U postgres -d postgres -c "CREATE DATABASE patra_catalog;"
  docker exec patra-postgres pg_restore -U postgres -d patra_catalog /tmp/patra_catalog_v05_full.dump
'
```

## 附录 B：断点续做表

失败后是"原地重跑"还是"走回滚流程"，按下表决策，不要凭感觉。

| 步骤 | 失败后能否原地重跑 | 说明 |
|---|---|---|
| 0 前置检查 | ✅ 随便重跑 | 纯只读 |
| 1 物理备份 | ✅ 重跑覆盖即可 | 重跑前删掉半截文件 |
| 2 CD 隔离 | ✅ 幂等 | `gh workflow disable` 重复执行无副作用 |
| 3 构建 | ✅ 重跑 | gradle / docker build 幂等；线上未受影响。若报 jar 不存在，多半是 portal-cd 抢跑清了 `build/`（见 3.1.5），等它跑完重跑 3.2 即可 |
| 4 停机 | ✅ 重跑 | `docker stop` 幂等 |
| 5 换库 | ⚠️ **部分成功可重跑** | 原子块里已成功的语句重跑会报 `database "patra_catalog" does not exist` 或 `already exists`——**这属预期**。先用 `SELECT datname, datallowconn FROM pg_database WHERE datname LIKE 'patra_catalog%'` 看清当前处在哪个中间态，再补执行缺的那几句，不必回滚 |
| 6 Flyway | ❌ **必须走回滚流程** | 迁移失败会在 `flyway_schema_history` 留 `success=f`，之后任何启动都要求 `flyway repair`。新库此时是空的，drop 重来（回滚 → 重走 5-6）比 repair 干净得多 |
| 7 回填 | ✅ **重跑 restore 即可** | `--single-transaction` 保证失败整体回滚，目标表回到全空。只有人工干预造成部分写入时才回滚 |
| 8 重导 | ⚠️ 分情况 | 下载层失败（NCBI 抖动）→ 沿用同 generation 重触发；写入层失败 → 走回滚流程，且重来时**必须换新 generation** |
| 9 验收 | ✅ 随便重跑 | 纯只读；验收不过 → 判断是数据问题（回滚）还是断言写错（改断言） |
| 10 收尾 | ✅ 幂等 | 清理是分期的，宁可晚删不要早删 |
