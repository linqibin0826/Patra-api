Patra CD 流水线设计 — Mac mini 自托管持续部署（MVP: registry）

📅 2026-06-07 🌿 worktree-setup-cd 👤 Lin 🎯 spec draft
关键决策摘要

为 Patra 搭建第一条持续部署（CD）链路：merge 到 main 后 GitHub Actions 自动构建 registry 服务的 Docker 镜像并推送到 GHCR，由常驻 Mac mini 的 self-hosted runner 拉取并用 OrbStack 部署，应用容器与现有基础设施容器（PostgreSQL / Nacos 等）并排运行。本版作为 MVP 只打通 registry 一个服务的端到端链路（容器化 → 构建 → 推送 → 部署 → 健康检查），验证通过后再把同一模式复制到其余服务与 portal。触发节奏为全自动 Continuous Deployment，并保留 workflow_dispatch 手动按钮用于重部署与回滚。

1. 背景与现状

Patra 已有完整的 CI（5 个 GitHub Actions workflow：ci.yml / portal-ci.yml / ci-docs.yml / claude.yml / claude-code-review.yml），覆盖后端单元 / Testcontainers 集成 / E2E 测试、JaCoCo 覆盖率，以及前端 Biome lint / tsc 类型检查 / Vitest / Playwright。但没有任何 CD——没有 workflow 会构建并部署「能跑的应用」。

当前运行布局存在落差：

  • 基础设施容器（PostgreSQL / Redis / Nacos / RocketMQ / MinIO / 可观测性栈）已在 Mac mini 的 OrbStack 里运行，靠 git pull + docker compose 同步，服务仅在 tailscale 内网暴露。
  • 5 个 Java 微服务 + Next.js portal 目前以 fat JAR / next dev 进程跑在开发者的 MacBook 本机，尚未容器化。

本次目标：把应用也部署到 Mac mini，使其成为一套一直在线、与 main 同步、可经 tailscale 访问的 dev 运行环境——MacBook 只负责写代码与调试。

核心约束：云端够不到内网

GitHub Actions 的云端 runner 跑在公网（微软机房），够不到 tailscale 内网的 Mac mini。如何打通这「最后一公里」是整个 CD 设计的核心，也是本次最值得学的一课。本设计的答案是：镜像走公网 GHCR 中转 + 部署交给常驻 Mac mini 的 self-hosted runner 本地执行（详见第 3 节）。

2. 范围边界

In Scope
  • registry 服务的 Dockerfile（运行镜像）
  • cd.yml workflow：build-and-push（云端）+ deploy（self-hosted）两个 job
  • docker-compose.apps.yaml：新 compose project patra-apps，定义 registry 容器并加入 patra-net
  • .env.apps：应用容器非敏感 dev 默认值（随仓库提交）
  • 密钥二分护栏：真密钥走 gitignore 的 .env.apps.secret + .gitignore 扩展 + .env.apps.secret.example 模板
  • Mac mini 上安装 self-hosted runner 为 launchd 常驻服务（安装脚本 + 文档）
  • compose-all.sh 扩展，纳入 apps stack
  • registry 端到端链路验证（含自动触发与手动回滚）
Out of Scope（本版不做）
  • 其余 4 个 Java 微服务（ingest / catalog / object-storage / gateway）——链路验证后复制同一模式
  • portal 容器化（技术栈不同，Next standalone，单独处理）
  • 自动回滚（本版用手动 workflow_dispatch 回滚指定 tag）
  • 零停机 / 滚动更新 / 蓝绿部署
  • 多环境分离（staging / prod）——只有 Mac mini 这一套 dev
  • 改动现有 ci.yml 等 CI workflow

3. 整体架构与数据流

整条链路由「merge 到 main」这一事件精确驱动，分两段：云端构建推送 → Mac mini 本地部署。两段之间靠公网的 GHCR 镜像仓库解耦——这是绕开「公网够不到内网」的关键。

self-hosted runner 的角色（关键认知）

self-hosted runner 不是「一直拉镜像」的进程，而是一个「等 GitHub 派活」的通用执行器：

  • 平时：runner 进程对 GitHub 发起出向长轮询「有没有标了 macmini 的 job 给我」，静静待命，几乎不耗资源。
  • 被派活时：当 deploy job 触发，GitHub 把它派给 Mac mini 的 runner，runner 把步骤拉下来在 Mac mini 本地执行——「拉镜像 + 重启容器」只是这次活儿里的命令，merge 一次才执行一次。
  • 为何装在 Mac mini：① 部署动作（docker compose up）必须在 Mac mini 本地发生；② 连接方向是出向，Mac mini 无需开任何入站端口、无需公网 IP，天然适配 tailscale 内网——这就是「零网络打洞」。
  • 常驻方式：装成 launchd 服务，开机自启、后台待命，确保任何时候 merge main 都立刻有机器接 deploy 活儿。
与「Watchtower 轮询」方案的本质区别

被否决的 Watchtower 方案是「Mac mini 一直盯着 GHCR 镜像看更新没」（轮询镜像）；本设计是「Mac mini 等 GitHub 派 job」（等事件）。后者由 merge 事件精确驱动，无轮询延迟，多服务编排与回滚都好控制。

4. 配置注入与网络拓扑

调查确认：registry 只用 Nacos 做服务发现、不用配置中心，所有配置散在本地 yml，且 prod profile 本就是为环境变量注入设计的（DB 连接等无默认值，必须 env 注入）。因此容器化策略非常干净：容器跑 prod profile + 环境变量覆盖占位符，无需引入 Nacos 配置中心。

应用容器加入现有外部网络 patra-net，用容器服务名访问基础设施（注意是容器内端口，不是宿主映射端口）：

安全（公开仓库红线）：密钥二分 + 护栏

本仓库是公开仓库，配置按敏感度物理二分，从机制上杜绝真密钥泄露：

  • .env.apps（进仓库）：只放非敏感 dev 默认值——DB 默认密码 123456、NACOS_HOST=nacos、端口等内网默认值。这些是人尽皆知的测试默认值，且服务仅在 tailscale 内网暴露、公网连不上，进公开仓库无害。
  • .env.apps.secret（gitignore，绝不进仓库）：装真敏感密钥——OpenAI / PubMed / Crossref / EPMC API key、PAT、私钥等。compose 用 env_file 同时加载它与 .env.apps。

三道防线：① 真 key 文件物理 gitignore，从源头不可能被 commit；② pre-commit 的 detect-secrets / detect private key 钩子兜底拦截 sk- 等密钥模式；③ .env.apps.secret.example 模板明确告知哪些 key 该放进 secret 文件，避免误写进 .env.apps。密钥另外绝不烤进镜像，一律运行时 env 注入；镜像不含凭据，故 GHCR 设 public 也不泄密。

本次 MVP 的 registry 只连内网 PG + Nacos，不需要任何真敏感密钥——二分机制是为将来 ingest 等需要外部 API key 的服务提前建好护栏。

5. CD 流水线详解

触发

cd.yml 触发条件：

  • on.push.branches: [main]，并用 paths 过滤只在 registry 相关路径变更时触发（避免无关改动也部署）。
  • on.workflow_dispatch，带一个可选 image_tag 输入，用于手动重部署或回滚到指定 git sha。
  • 不监听 pull_request——保证 self-hosted runner 永不执行未经审查的 fork 代码（见风险表）。

两个 job

  1. build-and-push（runs-on: ubuntu-latest，云端）：checkout → setup JDK 25 → gradle :patra-registry-boot:bootJar（复用 Actions 的 Gradle 缓存）→ docker login ghcr.io（用 Actions 自带的 GITHUB_TOKEN，有 packages:write 权限）→ docker build → push 双 tag。
  2. deploy（runs-on: [self-hosted, macmini]，needs: build-and-push）：在 Mac mini 本地 docker compose pull + up -d → 轮询健康检查，超时则 job 标红。

镜像 tag 与回滚

  • 双 tag：:<git-sha>（不可变，用于精确部署与回滚）+ :latest（指向最新 main）。
  • 部署默认用 :<git-sha>（本次 commit）。
  • 回滚 = workflow_dispatch 手动输入旧 sha，deploy job 部署该 tag。

健康检查与「测试」CD 本身

compose healthcheck 打 localhost:6000/actuator/health；deploy job up 之后轮询健康，超时标红。CD 流水线无法写单测，验证靠真跑一遍（详见文末 Done 判定）。现有 ci.yml 继续保证代码测试，CD 不重复跑。

6. 关键决策与备选

决策 1：应用容器化为 Docker 镜像（而非 fat JAR 进程）

5 个微服务 + portal 打成 Docker 镜像推 GHCR，Mac mini 用 OrbStack 运行，与现有基础设施容器统一管理，可按镜像 tag 一键回滚。

备选 A：fat JAR + launchd 进程 — 否决：进程管理土法、回滚靠手动备份、与已全容器化的基础设施割裂、无隔离。
结论：容器化是业界标准与最优最终形态，也最契合学习目标；代价（写 Dockerfile）可接受。

决策 2：self-hosted runner 在 Mac mini 本地部署（打通最后一公里）

在 Mac mini 装 GitHub self-hosted runner，deploy job 直接在本地执行 compose pull + up。runner 对 GitHub 出向连接，无需入站端口，天然适配 tailscale 内网。

备选 A：云端 runner + tailscale + SSH — 否决：需管理 TS auth key + SSH key 两份 secret，复杂度更高。
备选 B：Mac mini 轮询 / Watchtower — 否决：轮询延迟、多服务编排与回滚控制弱、可观测性差。

决策 3：全自动 Continuous Deployment（merge 即部署）

merge 到 main 自动触发完整链路，Mac mini 永远跟 main 同步；同时保留 workflow_dispatch 手动按钮用于重部署 / 回滚。

备选 A：半自动 Continuous Delivery（部署需人工点一下） — 否决：dev 环境目标就是「省心同步」，人工闸门反而是负担；手动按钮已覆盖「需要时人工介入」的场景。

决策 4：MVP 先打通 registry 一个服务

先用 registry（SSOT 注册中心，相对独立、又能验证容器连 PostgreSQL + Nacos）把整条链路跑通，再把同一模式复制到其余服务与 portal。

备选 A：一次做全 6 个应用 — 否决：首次搭建就同时调试 6 份 Dockerfile + 编排 + 链路，出问题排查面过大，违背小步快跑。

决策 5：CI 先 build jar → Dockerfile 只 COPY（而非多阶段内部构建）

CI 步骤用 Gradle 构建 bootJar（复用 Actions Gradle 缓存），Dockerfile 只 COPY jar 到 eclipse-temurin:25-jre 运行镜像。镜像构建快、Dockerfile 极简。

备选 A：多阶段 Dockerfile 内部 gradle build — 否决：任何地方都能 docker build 但慢、不复用 CI 缓存；在「CI 已有 Gradle 缓存」的前提下属次优。

决策 6：GHCR 包可见性设为 public

镜像不含任何密钥，public 让 Mac mini pull 免认证，最省事。

备选 A：private + Mac mini 配只读 PAT 登录 — 暂不采用：增加 secret 管理成本而无实际收益（镜像不泄密）；若日后介意可随时切换。

决策 7：密钥按敏感度二分 + 护栏（公开仓库防泄露）

进仓库的 .env.apps 只放非敏感 dev 默认值；真敏感密钥走 gitignore 的 .env.apps.secret，compose 用 env_file 同时加载二者。三道防线：真 key 文件物理 gitignore + pre-commit detect-secrets 兜底 + .env.apps.secret.example 模板引导。沿用现有 .env / .env.secret 约定，保留 git pull 同步便利。

备选 A：.env.apps 整个 gitignore + 只留 example 模板 — 否决：仓库零环境值确实最安全，但失去 git pull 自动同步、每改一次变量都要手动登 Mac mini，与现有「基础设施靠 git pull 同步」习惯不一致；而非敏感默认值进公开仓库本就无害，收益不抵成本。

7. 风险与缓解

风险等级缓解
公开仓库 + self-hosted runner 可能执行未经审查的 fork PR 代码（GitHub 官方明确警告） high cd.yml 只监听 push: main 与 workflow_dispatch，不监听 pull_request；main 受分支保护，只有维护者能合入。fork PR 的 CI 仍走云端 runner，绝不触达 self-hosted runner。
将来误把真敏感密钥（OpenAI / PubMed API key 等）写进随仓库提交的 .env.apps，泄露到公开仓库 high 密钥二分：真 key 一律走 gitignore 的 .env.apps.secret（物理隔离）；pre-commit detect-secrets / detect private key 兜底拦截；.env.apps.secret.example 模板引导正确归位；MVP registry 本身不含任何真 key。
容器服务名解析依赖基础设施容器在 patra-net 上的网络别名 mid 实现时核对各基础设施 compose 的 networks / 别名，用 docker network inspect patra-net 验证 postgres / nacos 可解析。
健康检查失败时新容器已替换旧容器（非零停机） mid MVP 接受短暂不可用；失败时 workflow 标红 + 手动 workflow_dispatch 回滚旧 sha。零停机为非目标。
Mac mini / runner 离线导致部署不发生 mid runner 装 launchd 开机自启；离线时 job 排队，runner 上线后自动执行。
registry 是否真正依赖 Redis 未定（配置有、依赖树疑似无） low 首次部署看启动日志：若 autoconfig 尝试连接并失败，则注入 REGISTRY_REDIS_URL 或排除自动配置；若 classpath 无 Redis starter，配置被忽略、不影响启动。
容器内连 postgres 用容器端口 5432（非宿主映射的 15432）易混淆 low .env.apps 中注释标明「容器内端口」；prod profile 用 REGISTRY_DB_URL 显式写全连接串。

Done 判定
  1. Mac mini 上 self-hosted runner 注册成功：GitHub repo Settings → Actions → Runners 显示 online，能接 macmini 标签的 job。
  2. workflow_dispatch 手动触发 cd.yml，build-and-push + deploy 两个 job 全绿。
  3. Mac mini docker ps 可见 patra-registry 容器 running 且 healthy。
  4. 经 tailscale curl http://linqibins-mac-mini:6000/actuator/health 返回 UP。
  5. 改一处无关代码 merge 到 main，观察 cd.yml 自动触发并完成部署，Mac mini 上容器更新为新镜像。
  6. 回滚验证：workflow_dispatch 输入上一个 git sha，部署回退到该版本。
