前端 portal CD — 设计文档

📅 2026-06-08 🌿 worktree-portal-cd 👤 Lin 🎯 spec draft
关键决策摘要

为 patra-portal(Next.js 15 / React 19 / Node 24)新建一条独立的 portal-cd.yml 持续部署流水线，与后端 cd.yml 平行、与 portal-ci.yml(质量门)职责分离。portal 是单个前端单元，无后端「多服务选择性构建+依赖排序」复杂度,故流水线为线性两段:ubuntu 上 pnpm 多阶段 docker build 推 GHCR → Mac mini self-hosted runner 上 compose pull + up + 健康检查。镜像用 output: "standalone" 自包含 Node server,运行时注入 PATRA_GATEWAY_BASE_URL 保持 BFF(gateway 地址只在容器内可见)。仅部署 Mac mini 容器(tailscale 内网),不碰 Vercel/公网。

1. 背景与现状

后端 5 个服务(registry / object-storage / catalog / ingest / gateway)的 CD 已全打通:cd.yml 走 detect-changes → 动态 matrix 构建 → Mac mini 选择性 compose 部署,服务清单 SSOT 在 patra-infra/cd/services.json,5 服务共享一份 Java 分层 jar 的 service.Dockerfile。

前端 patra-portal 目前只有 CI(portal-ci.yml:lint / typecheck / test / e2e),没有任何 CD/部署——没有 Dockerfile,不在 services.json,不在 docker-compose.apps.yaml,Mac mini 上没有它的容器。本次补齐这块缺口:把 portal 也纳入「merge 到 main → 自动构建 + 部署到 Mac mini」的闭环。

两个决定本设计走向的事实:(1) portal 是 BFF 架构——Next.js 服务端(RSC / Route Handler)读 PATRA_GATEWAY_BASE_URL 去调 gateway,地址绝不下发浏览器(.env.example 明令禁止 NEXT_PUBLIC_ 前缀),因此它必须以 Node server 运行,不能静态导出。(2) portal 与后端技术栈完全不同(pnpm/Node vs Gradle/Java),无法复用后端那套构建机制。

2. 范围边界

In Scope
  • 新建独立 .github/workflows/portal-cd.yml(build-and-push + deploy 两段)
  • 新建 patra-portal/Dockerfile(Next.js standalone 多阶段)
  • next.config.ts 加 output: "standalone"
  • docker-compose.apps.yaml 加第 6 个 service portal
  • 新建 patra-infra/docker/.env.portal(运行时坐标)
  • portal-ci.yml 去掉 push:main 触发(CI=PR 门禁,CD=main 部署)
  • 回滚:workflow_dispatch 带 image_tag 输入
Out of Scope
  • Vercel / 公网托管 / 公网 gateway ingress(本版只 Mac mini 容器)
  • detect-changes / 动态 matrix(单单元,用不上)
  • 把 portal 写进 services.json(那是后端构建 SSOT)
  • 加载 .env.common(Spring/Nacos/MinIO,portal 用不到)
  • 反向代理/统一域名/HTTPS 终止(tailscale 内网直接端口访问即可)

3. 总体架构

独立 portal-cd.yml 与后端 cd.yml 平行,与 portal-ci.yml 职责切分。因 portal 是单个前端单元,流水线是线性两段(无 detect-changes、无 matrix、无依赖排序):

push:main (paths: patra-portal/**)  或  workflow_dispatch
  │
  ├─ build-and-push   (runs-on: ubuntu-latest)
  │     pnpm 多阶段 docker build(内含 next build)
  │     → 推 GHCR  ghcr.io/linqibin0826/patra-portal:<sha> + :latest
  │
  └─ deploy           (runs-on: [self-hosted, macmini])
        写 GHCR 凭据(绕 macOS 钥匙串) → compose pull(3× 重试,抗 GHCR 代理 TLS 抖动)
        → docker compose up -d portal → host 侧 curl /api/health 轮询
  • 触发:push: main 且 paths: [patra-portal/**, .github/workflows/portal-cd.yml];workflow_dispatch(含 image_tag 输入,回滚用)。不监听 pull_request——self-hosted runner 永不跑未审查的 fork PR 代码(沿用 cd.yml 安全约束)。
  • 并发:concurrency: portal-cd-${{ github.ref }},cancel-in-progress: false(部署不可半路取消)。
  • 回滚:workflow_dispatch 填旧 image_tag → 跳过 build、直接 deploy 该 tag(对齐 cd.yml 语义)。
  • 安全:dispatch 输入通过 env: 传入 shell(不直接 ${{ }} 插值),避免脚本注入(沿用 cd.yml 加固写法)。

4. 镜像构建 — patra-portal/Dockerfile

后端 5 服务共享一份 Dockerfile(因为都是同构 Java jar);portal 自带 patra-portal/Dockerfile——Next.js 约定,紧贴源码,docker build 上下文 = patra-portal/。

前置:next.config.ts 加 output: "standalone",产出自包含 server(.next/standalone/server.js),镜像精简、运行时只需 Node。三阶段:

  1. deps:node:24-alpine + corepack 启用 pnpm,pnpm install --frozen-lockfile(独立层,锁文件不变则缓存命中)。
  2. builder:copy 源码 + pnpm build(standalone trace)。
  3. runner:node:24-alpine,非 root(uid 10001),copy .next/standalone + .next/static + public(standalone 不自动带后两者,必须手动 COPY);env PORT=4000 HOSTNAME=0.0.0.0 NODE_ENV=production;CMD ["node","server.js"]。
  • 镜像名 ghcr.io/linqibin0826/patra-portal,tag <sha> + latest(与后端同 GHCR 命名约定)。
  • 容器内健康检查用 busybox wget(alpine 自带,免装 curl)。
  • node 版本由 .nvmrc(24)与 package.json engines(>=24)锚定,Dockerfile 基镜像与之对齐。

5. 运行时编排与网络

portal 作为 patra-net 上第 6 个 app 容器加入现有 docker-compose.apps.yaml(不另开 compose 文件,app 栈集中管理):

  • image: ghcr.io/linqibin0826/patra-portal:${PORTAL_IMAGE_TAG:-latest}、container_name: patra-portal、ports: ["4000:4000"]、restart: unless-stopped。
  • env_file: [.env.portal, .env.portal.secret(required:false)] —— 不加载 .env.common。
  • compose healthcheck:容器内 wget -q -O - http://localhost:4000/api/health。
  • 新建 .env.portal(committed dev 默认,非敏感):PATRA_GATEWAY_BASE_URL=http://gateway:9528(patra-net 服务名 + 容器内端口)、PORT=4000、NODE_ENV=production。

数据流:浏览器 → http://<macmini-tailscale>:4000 → Next.js standalone server(RSC / Route Handler)→ 服务端 fetch http://gateway:9528(patra-net 内部)→ catalog。gateway 地址只在容器内可见、不下发浏览器(BFF 保持)。

健康检查契约

portal 已有 src/app/api/health/route.ts,GET 返回 HTTP 200 + {status:"ok",version,timestamp}。deploy 用 curl -fs http://localhost:4000/api/health 判定——-f 遇非 2xx 即失败,无需 grep body(后端那套 grep "status":"UP" 不适用,因 portal 返回 "ok" 非 "UP")。

6. 与现有 CI 切分

当前 portal-ci.yml 在 push:main 与 pull_request 双触发。引入 portal-cd 后,merge 到 main 会让 CI(lint/test,内含 next build)与 CD(docker 内又跑一次 next build)重复构建。

方案:去掉 portal-ci.yml 的 push:main 触发,只留 pull_request + workflow_dispatch。理由:main 受分支保护、PR 是质量门;切分为 CI = PR 门禁,CD = main 部署。这正是 portal-ci.yml 注释里已预想的方向。

7. 关键决策与备选

决策 1:独立 portal-cd.yml,不扩展后端 cd.yml

新建独立 workflow,后端 cd.yml / services.json 完全不动。镜像现有 ci.yml / portal-ci.yml 的前后端拆分,各自内聚。

备选 A:扩展 cd.yml 为多态(portal 进 services.json 加 type: node,build 按 type 分支 Gradle/pnpm) — 否决:给 Java-centric 的 cd.yml 引入一堆条件分支,detect-changes/matrix 对单单元是过度设计。
备选 B:cd.yml 里加专用 build-portal job — 否决:要给 cd.yml 加 patra-portal/** 触发路径,会耦合前后端触发、让 portal 改动多余地跑后端 detect-changes。

决策 2:Dockerfile 与 portal 源码同目录,不放 patra-infra/docker/

portal 的 Dockerfile 紧贴源码放 patra-portal/Dockerfile,build 上下文即 patra-portal/。

备选:放 patra-infra/docker/portal.Dockerfile(对齐后端集中放置) — 否决:后端 5 服务共享一份 Dockerfile 才集中放;portal 的 Dockerfile 与其源码强耦合(COPY package.json / 锁文件 / 源码),Next.js 惯例就近放更清晰。compose 只引用镜像、不关心 Dockerfile 位置。

决策 3:standalone 自包含镜像 + 运行时 env 注入

用 output: "standalone" 产出 Node server,PATRA_GATEWAY_BASE_URL 在容器启动时由 env 注入(非构建期 bake)。

备选 A:静态导出(next export)+ nginx — 否决:portal 是 BFF,服务端要代理 gateway、保持地址不下发浏览器,静态导出无服务端运行时,做不到。
备选 B:不开 standalone,镜像内 pnpm start — 否决:要把 node_modules 全量带进运行镜像,体积大;standalone 只带 trace 到的依赖。
注:此做法天然云可移植(将来可搬 Vercel/Cloud Run),但本版不为公网写任何东西——选它纯因为是 Next.js 容器化的正确做法。

决策 4:portal 加入 docker-compose.apps.yaml,不另开 compose 文件

portal 是一个 app,与后端 5 服务同属 app 栈、同在 patra-net,放进同一个 compose 文件统一编排,deploy 用 docker compose -f docker-compose.apps.yaml up -d portal。

备选:独立 docker-compose.portal.yaml — 否决:无必要的文件碎片化,portal 本就是 app 栈一员。

8. 风险与缓解

风险等级缓解
Mac mini 拉 portal 镜像过 Shadowrocket 代理,大层首拉间歇 TLS 损坏(tls: bad record MAC 等)。不能直连(够不到 GitHub)。 mid 复用后端 deploy 的 3× pull 重试循环;standalone node:alpine 镜像约 150–200MB,首拉失败重试/预拉即可,非硬墙。
standalone 用 node server.js 启动(非 pnpm script),/api/health 里 npm_package_version 取不到 → version 回退 "0.0.0"。 low 不影响健康判定(只看 HTTP 200)。本版不修(YAGNI);如需真实版本,可在 Dockerfile 注入 npm_package_version env。
去掉 portal-ci.yml 的 push:main 后,直接 push 到 main(非 PR)的 portal 改动不再跑 CI 质量门。 low main 已开分支保护、改动一律走 PR;portal-cd 自身在 docker build 内会跑 next build,构建失败即部署失败,兜底。
portal 容器起来但连不上 gateway(PATRA_GATEWAY_BASE_URL 配错 / gateway 未就绪),页面拉不到数据。 mid .env.portal 用 patra-net 服务名 gateway:9528(容器内端口);/api/health 不依赖 gateway,故健康检查仍 UP——需在 Done 判定里显式验证「页面能拉到 catalog 数据」而非只看容器 healthy。

9. 改造文件清单

#文件操作说明
1 .github/workflows/portal-cd.yml create 独立 CD 流水线:build-and-push(ubuntu/pnpm)+ deploy(macmini)。
2 patra-portal/Dockerfile create Next.js standalone 多阶段(deps / builder / runner)。
3 patra-portal/next.config.ts modify 加 output: "standalone"。
4 patra-infra/docker/docker-compose.apps.yaml modify 加第 6 个 service portal(image / port 4000 / env_file / healthcheck)。
5 patra-infra/docker/.env.portal create 运行时坐标:PATRA_GATEWAY_BASE_URL / PORT / NODE_ENV。
6 .github/workflows/portal-ci.yml modify 去掉 push:main 触发,只留 pull_request + workflow_dispatch。
7 patra-portal/.dockerignore create 排除 node_modules / .next / tests 等,缩小 build context。
Done 判定
  1. 本地可 docker build -f patra-portal/Dockerfile patra-portal 成功,docker run -e PATRA_GATEWAY_BASE_URL=... -p 4000:4000 起得来,/api/health 返回 200。
  2. merge 含 portal 改动的 PR 到 main → portal-cd 自动触发,build-and-push 成功推 GHCR。
  3. deploy job 在 Mac mini 上 compose pull + up patra-portal 容器,健康检查通过。
  4. tailscale 内 http://<macmini>:4000 可访问,页面能拉到 catalog 真实数据(BFF 链路通)。
  5. workflow_dispatch 填旧 image_tag 能回滚到指定镜像。
