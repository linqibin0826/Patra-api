v0.6 Catalog 作者与摘要数据链路修复

📅 2026-08-28 🌿 feat/v0.6-catalog-authors-abstracts 👤 linqibin 🎯 spec draft
关键决策摘要

v0.6 是纯后端 + 数据版本（portal 前端零改动）：① 补齐从未实现的文献作者落库三层（Processor→Writer→DAO），作者采用「行内存名 + 可空 ORCID 软关联」——关联表直接存展示名，绝不向 cat_author 新建行，作者库保持纯净；② 摘要以共享领域类型 PublicationAbstractSection 定型为有序数组并类型化序列化（根治双重编码与读写不一致），非结构化与混合摘要不再丢弃、结构化摘要统一生成 plain_text，两种形态一等公民，AlternativeAbstract 全链路对称改造；③ 数据重建采用「换库重建」：rename 旧库为回滚锚 → 新库 Flyway 重建最终形态 schema（直接改 V3）→ pg_dump 回填 publication 域之外的全部参考数据（期刊 / ROR / MeSH / 评级 / 作者库）→ 仅重导 baseline 文献（新增 generation identifying 参数绕开 Batch 实例冲突），验收走源数据闭环指标。

1. 背景与现状

mini 生产库 patra_catalog 现有 18,807 篇文献（2026-05-31 由 XXL-Job pubmedBaselineImportJob 从 NCBI 下载 pubmed26n1333.xml.gz 单文件导入），portal 文献详情页（v0.5 / PAP-45）的作者区与摘要区均为空。排查确认两条链路的缺陷：

作者：从未实现。Parser（CanonicalPublicationParsingStrategy.parseAuthorList）完整解析了 <AuthorList>（姓名 / ORCID / 机构 / EqualContrib），但 PubmedArticleItemProcessor 无 buildAuthorData()、PublicationItemWriter 无作者分支、PublicationAuthorDao 类不存在——数据解析进内存后无声丢弃。cat_publication_author 0 行；cat_author 的 49.7 万行来自另一条独立链路（authorImportJob 导入 PubMed Computed Authors 全局作者库，dev 配置限 50 万条），与文献无行级关联。项目自带的 pubmed-parsing-gap-analysis.md 早已将此标为 🔴 高优先级缺口；详情页读端 SQL 已写好 FROM cat_publication_author 在等数据。

摘要：四层缺陷叠加。① 写端把 sections 序列化为对象 {"LABEL":"text"}，读端 parseSections 期望数组 [{label,text}]——schema 从未对齐，解析失败被 catch 吞掉返回空数组（读空的主因）；② 存量 5,114 行摘要全部是双重编码的 JSON 字符串（commons Jackson3JsonFormatMapper String 透传修复前，手工 Jackson 2 序列化的字符串又被 Hibernate 二次序列化）；③ 批量路径从不生成 plain_text（API 路径的对照实现 PubmedPublicationConverter.extractAbstract 是正确的）；④ 无 Label 的非结构化摘要（PubMed 的大多数）被整条丢弃不落库——这是 27% 覆盖率（5,114/18,807）的主因，也解释了表内 100% 是 STRUCTURED。

关键环境事实（约束重建方案）。patra_catalog 库内除文献外还承载大量非本次目标的业务数据：15,434 期刊、120,445 ROR 机构、31,110 MeSH Descriptor + 324,016 SCR + 约百万 Entry Term、71,339 Scopus 评级及 JCR / CAS / LetPub 等富化数据——这些来自各自独立的导入 Job，重放代价高（多为大文件外网下载）。且文献导入依赖期刊先在库：PubmedArticleItemProcessor 查不到 venue 时直接丢弃该篇（:128）。另两条硬约束：两个 Batch Job 均 addTimestamp=false，同参数重跑会抛 JobInstanceAlreadyCompleteException；改动 V3 migration 后新镜像对旧库启动会因 Flyway checksum 不一致失败——重建必须按 maintenance runbook 编排，不能走常规 CD。

前端就绪。portal AuthorList / AbstractBlock 组件 v0.5 已就绪，AbstractBlock 对 empty / plain / structured 三态渲染齐备（section 的 label 为空时正常渲染正文），API 响应契约不变则 FE 零改动。

  • ORCID 归一化协议 + chunk 级批量软关联（命中 cat_author_orcid 填 author_id，未命中留空）
  • 共享领域类型 PublicationAbstractSection 定型有序数组 + Entity 字段类型化（删手工 mapToJson / jsonToMap）
  • 非结构化 / 混合摘要落库 + 统一 plain_text 生成；主摘要 Copyright 解析落库

  • 详情 + Feed 读端 SQL 改读行内作者名；parseSections 兜底日志 warn→error
  • pubmedBaselineImportJob 新增 generation identifying 参数（重导解锁）
  • mini「换库重建」maintenance runbook：rename 回滚锚 + 参考域数据回填 + 单 Job 重导 + 源数据闭环验收
Out of Scope

  • 作者检索 / 作者详情页
  • portal 前端改动（契约不变，FE 已就绪）
  • AI 速读（aiSummary 维持留空）
  • 扩大导入数据量（仍为单文件 pubmed26n1333，对齐现状）
  • 重放期刊 / ROR / MeSH / 评级等参考域导入 Job（数据经 pg_dump 回填，不重放）
  • authors_complete 标志改造——其语义是「PubMed 声明作者列表完整」，与 patra 是否落库无关，保持原样，仅此文档澄清语义

3. 作者落库链路

3.1 DDL（直接改 V3__create_author.sql）

  • cat_publication_author：author_id 改 NULL（软关联位）；新增行内列 display_name VARCHAR(200) NOT NULL、last_name、fore_name、initials、suffix、collective_name、orcid VARCHAR(19)（归一化后的原始 ORCID 存档，便于未来重关联 / 审计）。
  • 唯一性：uk_pub_author 改为部分唯一索引 UNIQUE (publication_id, author_id) WHERE author_id IS NOT NULL（继续阻止同一已消歧作者在同篇重复关联，又不受大量 NULL 干扰）；保留 uk_author_order (publication_id, author_order)。
  • cat_publication_author_affiliation：删除冗余 author_id 列（现为 NOT NULL，与可空软关联直接冲突；读端本就按 pub_author_id 查机构）。Entity 同步。

3.2 姓名快照规则

  • display_name 生成："LastName ForeName"；ForeName 缺则用 Initials（"LastName I"）；仅有 LastName 则单独成名；集体作者取 CollectiveName。超长按列宽截断（200）。
  • 集体作者：collective_name 存原文，姓名各列为空，display_name = 集体名。
  • ValidYN="N" 的作者照存不过滤（PubMed 语义为姓名更正记录，快照忠实于源）；suffix 存独立列不拼入 display_name。

3.3 ORCID 归一化与软关联

  • 归一化：去 https://orcid.org/ 等 URL 前缀 → 标准 XXXX-XXXX-XXXX-XXX[0-9X] 格式校验 + ISO 7064 校验位校验 → 校验失败视为无 ORCID（留空不关联，不落 orcid 列）。
  • 批量查询：Repository 按 chunk 收集本批全部归一化 ORCID，一次 IN 查询 cat_author_orcid 得 orcid → author_id 映射，内存回填——禁止 Processor 逐作者查库。
  • 绝不向 cat_author 新建行——作者库只属于 Computed Authors 导入链路，保持每行都是真正消歧过的人。

3.4 写链路（补齐三层）

  • 单一事实来源：作者快照列表只挂在 PublicationAggregate 上；PublicationImportResult / PublicationCompleteData 透传聚合引用，不另存 authors 副本。
  • Processor：新增 buildAuthorData()——author_order 从 1 递增、is_first_author = (order==1)、is_equal_contribution 取 XML EqualContrib、is_corresponding_author 恒 false（PubMed XML 无通讯作者显式标记，不造假数据）。
  • 父子 ID 与写入顺序：应用层预分配 PublicationAuthorEntity.id → 用它构造 affiliation 行的 pub_author_id → 先批量写 + flush 作者行 → 再批量写机构行。
  • Writer / Repository：新建 PublicationAuthorDao；PublicationRepositoryAdapter.insertAllWithAssociations 增加 writeAuthorAssociations（作者行 + 机构行批量写入，沿用 batchSaveWithFlush 模式）。

3.5 读端（详情 + Feed 一并改）

PublicationDetailDao.findAuthorsByPublicationId 与 PortalFeedDao 的作者查询都改读行内 pa.display_name、去掉 JOIN cat_author（否则未命中 ORCID 的作者会从首页卡片消失）；affiliation 子查询不变。API 响应字段结构不变（name / order / first / corresponding / affiliation），portal 零改动。

4. 摘要写读链路（两种形态一等公民）

4.1 共享领域类型与 schema 定型

  • domain 层新增唯一共享类型：record PublicationAbstractSection(String label, String text)（label 可为 null）。主摘要、AlternativeAbstract、Entity 序列化、读模型统一使用此定义——读写不可能再各说各话。
  • structured_sections 定为有序数组 [{"label","text"}]：保 section 顺序（顺序是语义）、容纳重复 label、容纳无 label 的混合段。
  • Domain VO PublicationAbstract.structuredSections 从 Map<String,String> 改 List<PublicationAbstractSection>；Map 语义 API（getSection / getSectionNames / containsKey）重设计为列表语义（按 label 查询返回 List，可表达重复 label）。
  • Entity 字段从 String + 手工 Jackson 2 序列化，改为 List<PublicationAbstractSection> + @JdbcTypeCode(SqlTypes.JSON)，交给全局 Jackson3JsonFormatMapper 单点序列化；删除 PublicationJpaMapper.mapToJson / jsonToMap（静默吞异常源），双重编码从机制上不可能再发生。
  • 纯文本摘要（无任何 section）的 structured_sections 统一存 SQL NULL（不是 []）。

4.2 写端分流（含混合形态）

  • 判型：≥1 个 section 带 Label → STRUCTURED；全部无 Label → UNSTRUCTURED（枚举已存在）。
  • STRUCTURED（含混合）：全部 section 按源顺序入数组，无 Label 段以 label=null 保位置不丢内容；同时生成 plain_text → ofBoth。
  • UNSTRUCTURED：文本按段落合并落 plain_text，sections 为 null → ofPlainText。不再丢弃——此项将摘要覆盖率从 27% 拉回源数据实际水平。
  • plain_text 统一由 Processor 一层生成：有 label 段 = "LABEL: text"、无 label 段 = text，段间以 \n 连接（与 API 路径对照实现对齐并统一分隔符）。
  • Copyright 闭环：主摘要 Parser 补解析 CopyrightInformation 落 copyright 列（列已存在）；AlternativeAbstract 的 copyright 字段一并打通（DDL 缺列则 V3 补上）。

4.3 AlternativeAbstract 全链路对称

现链路在进入 Domain 前已把 OtherAbstract 的 sections 拍平成文本——「对称改造」需展开为：CanonicalPublication.AlternativeAbstract 携带 sections 结构、AlternativeAbstractData 中间结构同步、PublicationImportResultMapper 映射同步、Parser / Processor 单测覆盖、独立的写读 round-trip IT。存储与主摘要共用 PublicationAbstractSection 数组 schema。

4.4 读端

读写共享同一 record 定义，数组直接反序列化；parseSections 吞异常兜底从 log.warn 升 log.error（重建后数据格式可信，再失败即 bug，必须响；仍返回空数组保详情页可用）。plain_text 直接透传。前端 AbstractBlock 按 deriveAbstract 自动三态渲染，label 为空的混合段正常显示正文，无需改动。

5. 数据重建与验证

5.1 换库重建 runbook（mini，维护窗口执行，非常规 CD）

  1. 构建：新 catalog 镜像构建完成但不启动（改过 V3 的新镜像对旧库启动必因 Flyway checksum 不一致失败，禁止直接走 CD 部署）。
  2. 停机：停 catalog 容器，确认 patra_catalog 无活跃连接。
  3. 回滚锚：ALTER DATABASE patra_catalog RENAME TO patra_catalog_v05_backup——旧库整体保留，验收通过前不删。
  4. 新库：CREATE DATABASE patra_catalog（空库）；启动新镜像 → Flyway 全量重跑（含改过的 V3，最终形态 schema，checksum 天然干净）。
  5. 参考域回填：pg_dump --data-only 从 backup 拷贝 publication 域之外的全部表——venue 域、ROR、MeSH 域（Descriptor / SCR / Entry Term / Tree）、评级与富化域（Scopus / JCR / CAS / LetPub…）、cat_author 家族（author / name_variant / orcid）。精确表清单在实现计划阶段逐表核定（原则：cat_publication* 全弃，其余全拷；cat_venue_publication_stats 等文献派生表归入弃列并在重导后重算或置空，计划阶段定）。回填后跑行数对照脚本：backup 与新库的每张回填表行数一致。
  6. 重导文献：pubmedBaselineImportJob（fileIndex=1333）以新增的 generation=v0.6 identifying 参数启动（绕开 JobInstanceAlreadyCompleteException；authorImportJob 无需重跑——cat_author 家族已回填）。patra_batch 元数据库不动。
  7. 验收：按 §5.3 源数据闭环指标核对；portal 页面人工确认。
  8. 收尾 / 回滚：验收通过 → backup 库保留观察期后删除；任一步失败 → 停新容器、rename 回 patra_catalog、重新部署旧镜像（完整回滚）。

5.2 测试策略

  • 单测：Parser→Processor 摘要判型三态（纯文本 / 结构化 / 混合）与 plain_text 生成；buildAuthorData（普通 / 集体作者、EqualContrib、order 递增、姓名快照规则各分支）；ORCID 归一化（前缀 / 校验位 / 非法值）与命中 / 未命中软关联。
  • 写读 round-trip IT（真实链路闭环）——精确断言矩阵：
    • 落库后 jsonb_typeof(structured_sections) = 'array'，无外层 JSON string；
    • section 顺序保持；重复 Label 两条都在；混合摘要的 label=null 段保留；
    • plain_text 与预期精确一致；纯文本摘要 structured_sections IS NULL；
    • 主摘要与 AlternativeAbstract 两条链路分别覆盖；
    • 双读路径都能恢复：Entity→Domain（FormatMapper 反序列化）与 native ::text→ReadAdapter（parseSections）；
    • 作者：写入后详情 / Feed SQL 读出行内名、order 连续、ORCID 命中行 author_id 非空、affiliation 按 pub_author_id 挂接无孤儿。

5.3 验收指标（源数据闭环，替代固定阈值）

  • 对同一份 pubmed26n1333.xml.gz 跑统计脚本，与库内核对：源 XML 中含 AbstractText 且成功导入的文献数 = 库内有摘要文献数；源 XML 有效 Author 数 = cat_publication_author 行数。
  • ORCID 报告：源含 ORCID 作者数 / 归一化通过数 / 软关联命中数 / 未命中数，逐项列出。
  • 结构完整性：每篇 author_order 连续且唯一、第一作者恰好一人；affiliation 无孤儿行；Batch skip count = 0。
  • curl 详情端点抽查：结构化篇 sections+plainText 双非空、非结构化篇 plainText 非空且 sections 为 null、混合篇无 label 段保留、作者列表非空且序正确。
  • portal 文献详情页人工确认：作者区与摘要区（两种形态）渲染真实数据。

6. 关键决策与备选

决策 1：换库重建（rename 回滚锚 + 参考域回填 + 单 Job 重导）

patra_catalog 同库承载期刊 / ROR / MeSH / 评级等大量非目标数据，且文献导入依赖期刊先在库。重建采用：旧库 rename 为回滚锚 → 新库 Flyway 重建最终形态 schema → pg_dump 回填 publication 域之外全部数据 → 仅重导 baseline 文献。全程有完整回滚路径。

备选 A：drop 整库 + 只重导 author 与 baseline — 否决：会清空 v0.5 期刊业务与全部参考数据，且期刊为空时文献导入直接丢弃所有篇（初稿方案，评审捕获）。
备选 B：drop 整库 + 全量重放所有导入 Job — 否决：ROR / MeSH / 评级 / Computed Authors 源文件重下体量巨大（数 GB 级、代理出口慢），重放耗时不可控且无必要。
备选 C：保留原库 + 存量迁移脚本 — 否决：需在活库上做 schema 变更 + 数据修复双重迁移，违反绿地原则且复杂度最高。

决策 2：作者采用「行内存名 + 可空 ORCID 软关联」；affiliation 删冗余 author_id

关联表直接存展示名（详情页 100% 有作者可显示、不依赖 join），author_id 可空、仅 ORCID 命中时填，绝不因导文献向 cat_author 新建行——作者库保持纯净，作者检索能力不被重复行破坏。未来证据关联只需回填 author_id。机构表删除 NOT NULL 的冗余 author_id 列（与可空软关联冲突；读端本就按 pub_author_id 查）。

备选 A：ORCID 匹配 + 未命中新建 cat_author — 否决：PubMed ORCID 覆盖率仅两三成，作者库会被无法消歧的重复行淹没，作者检索废掉（用户明确否决）。
备选 B：Computed Authors PMID 证据精确关联 — 否决（本版）：独立大项目体量，且快照覆盖不到新文献；schema 已留回填位。

决策 3：共享 record PublicationAbstractSection + 有序数组 + 类型化序列化

domain 层唯一 section 定义贯穿主摘要 / AlternativeAbstract / Entity / 读模型；数组保序、容纳重复与无 label 段；Entity 类型化后由全局 Jackson3JsonFormatMapper 单点序列化，schema 不一致与双重编码从机制上消除。Map 语义 API 全部重设计为列表语义。

备选 A：保持对象形态、改读端适配 — 否决：Map 丢 section 顺序（顺序是语义）、重复 / 无 label 无法表达。
备选 B：保持 String 字段 + 集中手工 codec — 否决：仍是双轨序列化，静默吞异常隐患仍在。

决策 4：直接改 V3 baseline migration，不新增 ALTER migration

换库重建使 Flyway 在新库从零重跑，checksum 天然干净；绿地原则下 schema 按最终形态维护单一版本。配套约束：新镜像绝不能对旧库启动（runbook 第 1 步固化）。

备选：新增 V-next ALTER migration — 否决：为一次性重建保留演化台账没有价值，违背「只维护当前版本」纪律。

决策 5：is_corresponding_author 恒 false

PubMed XML 无通讯作者显式标记（通讯信息散落在 affiliation / email 中不可靠），不做启发式推断、不造假数据；列保留，等未来更可靠数据源。

备选：从 affiliation 文本 / email 启发式识别 — 否决：准确率无保障，错标比不标更误导。

决策 6：Batch 重导解锁用新增 generation identifying 参数

两个 Job 均 addTimestamp=false，同参数重跑抛 JobInstanceAlreadyCompleteException。为 pubmedBaselineImportJob 增加可选 generation identifying 参数（缺省行为不变，保留断点续传语义），一次改造长期受益于任何重导场景。

备选 A：定向删除 patra_batch 中该 JobInstance 元数据 — 否决：手工动共享元数据库，易错且每次重导都要再来一遍。
备选 B：新建 patra_batch_v06 元数据库 — 否决：为一个参数问题引入整库分裂，运维面翻倍。

7. 风险与缓解

风险等级缓解
NCBI baseline 目录年度轮换导致 pubmed26n1333.xml.gz 下线，重导拿不到同一文件 mid 执行重建前先 HEAD 探测文件存在性；若已下线则改用当年 baseline 对应文件（数据集变化可接受，v0.6 目标是修链路不是保数据快照）
pg_dump 参考域回填漏表 / 漏行，新库悄悄缺参考数据 high 回填清单在计划阶段逐表核定（原则：cat_publication* 全弃、其余全拷）；回填后强制跑行数对照脚本，backup 与新库逐表一致才允许进入重导步骤
新镜像被误经常规 CD 部署到旧库，Flyway checksum 失败触发反复回滚 mid runbook 明确「构建不部署」；维护窗口内先完成换库再放行部署；v0.6 合并与重建操作同窗口执行
mini 出站走代理，重下 baseline（~200MB）慢或中断 low 仅需重下这一个文件（参考域数据回填不走外网）；中断重跑 Job 即可（Spring Batch 断点续传）
VO Map→List 与作者聚合改动波及面（API 路径 converter 等调用方） low 编译期全量暴露即修；check + integrationTest 双门控兜底
作者行数量级（10 万+ 行）拖慢导入 low 沿用 batchSaveWithFlush 批量写（keyword 7.5 万行同模式无压力）；离线 Job 时长非敏感
