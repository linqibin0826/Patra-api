v0.6 Catalog 作者与摘要数据链路修复

📅 2026-08-28 🌿 feat/v0.6-catalog-authors-abstracts 👤 linqibin 🎯 spec draft
关键决策摘要

v0.6 以后端为主、Portal 一处最小改动：① 补齐从未实现的文献作者落库三层，作者采用「行内存名 + 可空 ORCID 软关联」——快照类型挂在聚合上（唯一事实来源、DELETE/INSERT 替换语义），绝不向 cat_author 新建行，机构表删除冗余 author_id 并级联清理其 DAO / IT；② 摘要以 catalog-domain 的共享类型 PublicationAbstractSection 定型有序数组（Canonical 层用自身 section 类型、Processor 处映射，避免反向依赖），非结构化与混合摘要不再丢弃，plain_text 由 Processor 统一生成，AlternativeAbstract 全链路对称，Portal 对 label=null 做最小渲染适配；③ 数据重建走「换库重建」maintenance runbook：pg_dump 物理备份保险 → CD 以 gh workflow disable cd.yml 显式隔离 → 旧库 rename 回滚锚 → 新库 Flyway 重建 → 显式 allowlist 回填参考数据（排除 flyway_schema_history）→ 以 generation identifying 参数重导 baseline，回滚为三库名交换 + 旧镜像 tag 复位，验收走「成功导入 PMID 集合」口径的源数据闭环。

1. 背景与现状

mini 生产库 patra_catalog 现有 18,807 篇文献（2026-05-31 由 XXL-Job pubmedBaselineImportJob 从 NCBI 下载 pubmed26n1333.xml.gz 单文件导入；该次 Batch 统计 read=30000 / write=18815 / filter=11185——filter 主要为期刊未命中被丢弃），portal 文献详情页（v0.5 / PAP-45）的作者区与摘要区均为空。排查确认两条链路的缺陷：

作者：从未实现。Parser（CanonicalPublicationParsingStrategy.parseAuthorList）完整解析了 <AuthorList>（姓名 / ORCID / 机构 / EqualContrib），但 PubmedArticleItemProcessor 无 buildAuthorData()、PublicationItemWriter 无作者分支、PublicationAuthorDao 类不存在——数据解析进内存后无声丢弃。cat_publication_author 0 行；cat_author 的 49.7 万行来自另一条独立链路（authorImportJob 导入 PubMed Computed Authors 全局作者库，dev 配置限 50 万条），与文献无行级关联。项目自带的 pubmed-parsing-gap-analysis.md 早已将此标为 🔴 高优先级缺口；详情页读端 SQL 已写好 FROM cat_publication_author 在等数据。

摘要：四层缺陷叠加。① 写端把 sections 序列化为对象 {"LABEL":"text"}，读端 parseSections 期望数组 [{label,text}]——schema 从未对齐，解析失败被 catch 吞掉返回空数组（读空的主因）；② 存量 5,114 行摘要全部是双重编码的 JSON 字符串（commons Jackson3JsonFormatMapper String 透传修复前，手工 Jackson 2 序列化的字符串又被 Hibernate 二次序列化）；③ 批量路径从不生成 plain_text（API 路径的对照实现 PubmedPublicationConverter.extractAbstract 是正确的）；④ 无 Label 的非结构化摘要（PubMed 的大多数）被整条丢弃不落库——这是 27% 覆盖率（5,114/18,807）的主因，也解释了表内 100% 是 STRUCTURED。

关键环境事实（约束重建方案）。patra_catalog 库内除文献外还承载大量非本次目标的业务数据：15,434 期刊、120,445 ROR 机构、31,110 MeSH Descriptor + 324,016 SCR + 约百万 Entry Term、71,339 Scopus 评级及 JCR / CAS / LetPub 等富化数据、296,600 行 cat_venue_publication_stats（baseline 导入不重建）——这些来自各自独立的导入 Job，重放代价高。且文献导入依赖期刊先在库：PubmedArticleItemProcessor 查不到 venue 时直接丢弃该篇。三条硬约束：两个 Batch Job 均 addTimestamp=false，同参数重跑抛 JobInstanceAlreadyCompleteException；改 V3 后新镜像对旧库启动必因 Flyway checksum 不一致失败；cd.yml 会在 main 的 patra-api/** 变化后自动 build + deploy——不隔离 CD，合并即自动撞旧库。重建必须按 maintenance runbook 编排。

前端现状。portal AuthorList / AbstractBlock 组件 v0.5 已就绪，empty / plain / structured 三态渲染齐备；但 TS 类型 label: string 且 AbstractBlock 无条件渲染 92px 标签列——混合摘要的 label=null 段需要一处最小适配（见 §5）。

3. 作者落库链路

3.1 DDL（直接改 V3__create_author.sql）

  • cat_publication_author：author_id 改 NULL（软关联位）；新增行内列 display_name VARCHAR(200) NOT NULL、last_name、fore_name、initials、suffix、collective_name、orcid VARCHAR(19)（归一化后的 ORCID 存档）。
  • 唯一性：Flyway 用部分唯一索引 CREATE UNIQUE INDEX ... ON cat_publication_author (publication_id, author_id) WHERE author_id IS NOT NULL；Entity 删除对应 @UniqueConstraint（JPA 注解表达不了 partial index），仅保留 uk_author_order (publication_id, author_order)。
  • cat_publication_author_affiliation：删除冗余 author_id 列及其索引 idx_author（读端本就按 pub_author_id 查机构）。级联清理：PublicationAuthorAffiliationDao 删除 / 重写全部 findAllByAuthorId* 派生方法（否则 Spring Data 启动抛 PropertyReferenceException）、Entity 删字段与过时 JavaDoc、PublicationAuthorAffiliationDaoIT 重写依赖 authorId 的用例、详情 / Feed IT 的机构测试数据构造同步更新。
  • affiliation_order：每位作者的多个机构从 1 连续编号、保持 XML 顺序（Entity 默认值不可依赖，显式赋值，否则撞 UNIQUE(pub_author_id, affiliation_order)）。

3.2 聚合快照类型与生命周期

  • domain 新增 VO：PublicationAuthorSnapshot（order / 姓名各字段 / display_name / orcid / authorId 可空 / 标记位 / affiliations 列表）与 PublicationAuthorAffiliationSnapshot（order / affiliation_string）。
  • PublicationAggregate 的 create / restore 增加作者快照参数，紧凑构造防御性拷贝（List.copyOf）；作者快照是唯一事实来源，PublicationImportResult / PublicationCompleteData 透传聚合引用不存副本。
  • Repository 生命周期闭环：findById / findByPmid 恢复聚合时加载作者 + 机构快照；已存在聚合再次保存时作者采用整体替换语义（DELETE 后 INSERT）；写入→恢复的聚合 round-trip IT 覆盖。

3.3 姓名快照规则

  • 所有姓名字段先 trimToNull；全部姓名字段与 CollectiveName 均为空 → 该作者跳过不落库，跳过数纳入验收报告。
  • display_name 生成："LastName ForeName"；ForeName 缺则 "LastName Initials"；仅 LastName 则单独成名；集体作者取 CollectiveName。超长按 200 截断；落库值不允许 NULL / 空白。
  • 集体作者：collective_name 存原文，姓名各列为空；ValidYN="N" 照存不过滤；suffix 存独立列不拼入 display_name。

3.4 ORCID 归一化与软关联

  • 归一化流水线：去 https://orcid.org/ 等 URL 前缀 → 转大写 → 标准 XXXX-XXXX-XXXX-XXX[0-9X] 格式校验 + ISO 7064 校验位校验 → 失败视为无 ORCID（orcid 列与 author_id 均留空）。
  • DAO 契约：新增轻量投影 interface OrcidAuthorIdView { String getOrcid(); Long getAuthorId(); } 与 AuthorOrcidDao.findAuthorIdsByOrcidIn(Collection<String>)——禁止复用会加载完整 Author + variants + orcids 的查询；查询条件限定作者 status = ACTIVE 且未软删（不关联 MERGED / INACTIVE / deleted）。
  • 执行约束：每个 chunk 恰好一次批查（收集本批全部归一化 ORCID → 一次 IN → 内存回填）；禁止 Processor 逐作者查库。
  • 绝不向 cat_author 新建行；ORCID 原始数 / 归一化通过数 / 命中数 / 未命中数 / 非法数全部纳入验收报告。

3.5 写链路与读端

  • Processor：buildAuthorData() 按 §3.3 规则产出快照——author_order 从 1 递增、is_first_author = (order==1)、is_equal_contribution 取 XML EqualContrib、is_corresponding_author 恒 false（PubMed XML 无显式标记，不造假数据）。
  • 父子 ID 与写入顺序：应用层预分配 PublicationAuthorEntity.id → 构造 affiliation 行 pub_author_id → 先批量写 + flush 作者行 → 再批量写机构行（沿用 batchSaveWithFlush）。
  • 读端（详情 + Feed）：PublicationDetailDao.findAuthorsByPublicationId 与 PortalFeedDao 作者查询都改读行内 pa.display_name、去 JOIN cat_author。语义变化：作者展示为文献快照，不再受 cat_author 的 soft delete / MERGED / INACTIVE 影响——相关现有 IT 按新语义改写。API 响应字段结构不变。

4. 摘要写读链路（两种形态一等公民）

4.1 类型边界与 schema 定型

  • 模块边界：CanonicalPublication 在 patra-common-model，不得反向依赖 catalog-domain。Canonical 层使用自身的 CanonicalPublication.AbstractSection（含 AlternativeAbstract 的 sections 不再拍平）；Processor 是唯一映射点：Canonical AbstractSection → catalog-domain PublicationAbstractSection；Processor 之后（主摘要 / AlternativeAbstract / Entity / ReadModel）统一使用 record PublicationAbstractSection(String label, String text)（label 可空）。
  • structured_sections 定为有序数组 [{"label","text"}]：保序、容纳重复 label 与无 label 段；纯文本摘要（无任何 section）统一存 SQL NULL（不是 []）。
  • Domain VO PublicationAbstract.structuredSections 从 Map<String,String> 改 List<PublicationAbstractSection>；Map 语义 API（getSection / getSectionNames / containsKey）重设计为列表语义（按 label 查询返回 List）。
  • Entity 字段改 List<PublicationAbstractSection> + @JdbcTypeCode(SqlTypes.JSON)，交全局 Jackson3JsonFormatMapper 单点序列化；删除 mapToJson / jsonToMap；JSONB 注解统一：columnDefinition 统一为 "jsonb"（与 Flyway 一致），主 / 替代摘要两个 Entity 都改。

4.2 写端分流（含混合形态）

  • Label 规范化先行：Label="" 或空白先规范化为 null。判型：≥1 个 section 满足 label != null && !label.isBlank() → STRUCTURED；否则 → UNSTRUCTURED（枚举已存在）。
  • STRUCTURED（含混合）：全部 section 按源顺序入数组，无 label 段以 label=null 保位置不丢内容；同时生成 plain_text → ofBoth。
  • UNSTRUCTURED：文本按段落合并落 plain_text，sections 为 null → ofPlainText。不再丢弃。
  • plain_text 统一由 Processor 生成：有 label 段 = "LABEL: text"、无 label 段 = text，段间 \n 连接。
  • Copyright 闭环：主摘要 Parser 补解析 CopyrightInformation 落 copyright 列（列已存在）；AlternativeAbstract 的 copyright 打通——注意其列属 V2__create_publication.sql，缺列则改 V2。

4.3 AlternativeAbstract 全链路对称

展开为：patra-common-model/CanonicalPublication.java（AlternativeAbstract 携带 sections 结构）→ Parser 不拍平 → AlternativeAbstractData / PublicationImportResultMapper 同步 → PublicationAlternativeAbstract VO 与 Entity 类型化 → Parser / Processor 单测 + 独立写读 round-trip IT。存储与主摘要共用 PublicationAbstractSection 数组 schema。

4.4 读端

读写共享同一 record 定义，数组直接反序列化。parseSections 签名改为携带上下文：parseSections(long publicationId, String abstractType, String json)——解析失败 log.error 记 publicationId + abstractType + 完整异常对象（不打印摘要正文），仍返回空数组保详情页可用；配套测试：malformed JSON → sections 降级为空、plainText 照常返回、日志可定位。

5. Portal 最小改动（混合摘要渲染）

  • TS 类型：AbstractSection.label 从 string 改 string | null（src/types/portal.ts）。
  • AbstractBlock：label=null 的段不渲染 92px 标签列节点，正文跨满整行（桌面与移动一致）；有 label 段渲染不变。
  • 测试：混合摘要（有 / 无 label 段交错）组件测试；重建后浏览器人工验收纳入 Done。
  • 除此之外 Portal 零改动（作者区 / Feed 契约不变）。

6. 数据重建与验证

6.1 换库重建 runbook（mini，维护窗口执行，非常规 CD）

  1. 物理备份保险：pg_dump -Fc patra_catalog 落盘（custom archive），记录大小与 SHA-256，pg_restore --list 验证归档可读。rename 只是同 volume 回滚锚，此备份是独立保险。
  2. CD 隔离：合并 v0.6 PR 之前执行 gh workflow disable cd.yml（backend CD 整体停用；learn / portal CD 不受影响）。合并后 CD 不会自动构建部署。记录当前运行中的旧镜像 tag（回滚复位用）。
  3. 构建不部署：mini 上从合并后的 main 手工 docker build 出 catalog 新镜像并打不可变 tag（如 catalog:v0.6-<sha>），不启动。
  4. 停机：停 catalog 容器，确认 patra_catalog 无活跃连接（catalog 停止即无 XXL executor 注册，恢复期 Job 不会触发）。
  5. 换库：ALTER DATABASE patra_catalog RENAME TO patra_catalog_v05_backup → CREATE DATABASE patra_catalog。
  6. Flyway 先行：以新镜像启动 catalog，仅让 Flyway 全量跑完（含改过的 V3，新库自生成全新 history / checksum）→ 核对 flyway_schema_history → 再次停止 catalog。
  7. 离线回填参考数据：pg_dump（custom archive，--data-only）按显式 allowlist 从 backup 导出参考表 → pg_restore --single-transaction 恢复进新库。约束：allowlist 在实现计划阶段逐表落名（原则：cat_publication* 全排除、flyway_schema_history 必须排除、cat_venue_publication_stats 明确保留——296,600 行 baseline 不重建）；恢复前目标表必须为空；恢复后逐表行数与 backup 一致才允许进入下一步。
  8. 启动与重导：启动 catalog（新镜像）→ pubmedBaselineImportJob（fileIndex=1333）以 generation 参数启动（规则见 §6.2；authorImportJob 无需重跑——cat_author 家族已回填）。patra_batch 元数据库不动。
  9. 验收：按 §6.4 指标核对；portal 页面人工确认。
  10. 收尾 / 回滚：验收通过 → gh workflow enable cd.yml，backup 库保留观察期后删除。任一步失败 → 回滚交换（三库名，避免重名冲突）：停 catalog → patra_catalog → patra_catalog_v06_failed_<timestamp> → patra_catalog_v05_backup → patra_catalog → 以第 2 步记录的旧镜像 tag 启动 → 验证旧镜像 + 旧库正常 → 排查后再战。

6.2 generation 参数（调用链与 attempt 规则）

  • 调用链全打通：XXL-Job 参数解析 → PublicationBaselineImportCommand → PublicationImportParams → PublicationBatchPort → PublicationImportJobParams.generation（identifying）→ Job 启动。缺省不传 = 现行为不变（断点续传语义保留）。
  • attempt 规则：同一新库导入失败后续跑 → 沿用同一 generation（利用断点续传）；回滚后重新从空库再战 → 必须换新 generation（如 v0.6-attempt2），否则会从旧 checkpoint 续跑造成前半段数据缺失。禁止把 generation 写死在代码里。

6.3 测试策略

  • 单测：摘要判型三态（纯文本 / 结构化 / 混合，含 Label 空串规范化）与 plain_text 生成；buildAuthorData（普通 / 集体作者、EqualContrib、order 递增、姓名规则各分支、全空跳过）；ORCID 归一化（前缀 / 大写 / 校验位 / 非法值）。
  • 写读 round-trip IT（真实链路闭环）——断言矩阵：
    • 落库后 jsonb_typeof(structured_sections) = 'array'，无外层 JSON string；
    • section 顺序保持；重复 Label 两条都在；混合摘要 label=null 段保留；
    • plain_text 精确一致；纯文本摘要 structured_sections IS NULL；
    • 主摘要与 AlternativeAbstract 两条链路分别覆盖；
    • 双读路径都能恢复：Entity→Domain（FormatMapper）与 native ::text→ReadAdapter（parseSections）；malformed JSON 降级 + 日志可定位；
    • 作者：写入→findById 恢复聚合快照完整（round-trip）；详情 / Feed SQL 读出行内名；order 连续；ORCID 命中行 author_id 非空；两机构作者的 affiliation_order 从 1 连续且无孤儿；Feed 快照不受 cat_author soft delete / MERGED 影响（新语义 IT）。

6.4 验收指标（源数据闭环，「成功导入 PMID 集合」口径）

  • 基准集合 = 本次成功写入的 PMID 集合（Batch write 计数对账，filter 丢弃的期刊未命中篇不计入）。对同一份 pubmed26n1333.xml.gz 跑统计脚本核对：基准集合内含 AbstractText 的文献数 = 库内有摘要文献数；基准集合内通过姓名规则的 Author 数 = cat_publication_author 行数（姓名全空跳过数单独列）。
  • ORCID 报告：源含 ORCID 作者数 / 归一化通过数 / 非法数 / 软关联命中数 / 未命中数，逐项列出。
  • 结构完整性：每篇 author_order 连续且唯一、有作者的文献恰好一位 first author、display_name 无 NULL / 空白；affiliation 无孤儿且每作者 order 从 1 连续；Batch skip count = 0。
  • curl 详情端点抽查：结构化篇 sections+plainText 双非空、非结构化篇 plainText 非空且 sections 为 null、混合篇无 label 段保留、作者列表非空且序正确。
  • portal 文献详情页与首页 Feed 人工确认：作者与摘要（含混合形态渲染）真实数据。

7. 关键决策与备选

决策 1：换库重建（物理备份 + rename 回滚锚 + allowlist 回填 + 单 Job 重导）

patra_catalog 同库承载期刊 / ROR / MeSH / 评级等大量非目标数据，且文献导入依赖期刊先在库。重建采用：pg_dump 物理备份保险 → 旧库 rename 为回滚锚 → 新库 Flyway 重建最终形态 schema → 显式 allowlist 离线回填参考数据（排除 flyway_schema_history，新库 history 自生成）→ 仅重导 baseline 文献。回滚为三库名交换 + 记录在案的旧镜像 tag 复位。

备选 A：drop 整库 + 只重导 author 与 baseline — 否决：清空 v0.5 期刊业务与全部参考数据，期刊为空时文献导入全数丢弃（初稿方案，评审捕获）。
备选 B：drop 整库 + 全量重放所有导入 Job — 否决：源文件重下体量巨大且 cat_venue_publication_stats 等无 Job 可重建。
备选 C：保留原库 + 存量迁移脚本 — 否决：活库上 schema 变更 + 数据修复双重迁移，违反绿地原则且复杂度最高。

决策 2：CD 隔离用 gh workflow disable，不改 cd.yml

cd.yml 在 main 的 patra-api/** 变化后自动 build + deploy，合并 v0.6 即自动把新镜像怼到旧库触发 Flyway 失败循环。隔离机制：合并前 gh workflow disable cd.yml，换库完成验收后 enable 恢复；新镜像由 mini 手工构建不可变 tag。一次性维护动作，不为此给流水线加常态化 maintenance 模式。

备选 A：cd.yml 增加 build-only / maintenance 输入模式 — 否决：为一次性场景增加流水线复杂度（YAGNI）。
备选 B：PR commit 上预构建镜像、换库后合并 — 否决：镜像与合并后 main 的 SHA 脱钩，溯源混乱。

决策 3：作者「行内存名 + 可空 ORCID 软关联」；快照挂聚合、affiliation 删冗余 author_id

关联表直接存展示名（详情页 100% 有作者、读端不依赖 join），author_id 可空、仅 ORCID 命中 ACTIVE 未删作者时填，绝不因导文献向 cat_author 新建行。快照 VO 挂在 PublicationAggregate 上（唯一事实来源，DELETE/INSERT 替换语义，restore 完整恢复）。机构表删除 NOT NULL 的冗余 author_id 列并级联清理 DAO / IT。作者展示语义变为文献快照，不受作者库后续合并 / 停用影响。

备选 A：ORCID 匹配 + 未命中新建 cat_author — 否决：作者库被无法消歧的重复行淹没，检索废掉（用户明确否决）。
备选 B：Computed Authors PMID 证据精确关联 — 否决（本版）：独立大项目体量；schema 已留回填位。

决策 4：section 类型分层——Canonical 层自持，catalog-domain 共享 record，Processor 唯一映射点

CanonicalPublication（patra-common-model）用自身 AbstractSection 携带结构（含 AlternativeAbstract 不拍平）；catalog 侧统一用 PublicationAbstractSection(label, text)（label 可空），Processor 做单点映射——避免 common-model 反向依赖 catalog-domain 的循环。数组保序、容纳重复与无 label 段；Entity 类型化 + columnDefinition="jsonb" 统一，由全局 FormatMapper 单点序列化。

备选 A：共享 record 放 common-model 全局复用 — 否决：把 catalog 的读写 schema 上提为跨服务契约，扩散耦合面。
备选 B：保持 String 字段 + 集中手工 codec — 否决：双轨序列化，静默吞异常隐患仍在。

决策 5：直接改 V3（及 V2 的 alternative copyright 列），不新增 ALTER migration

换库重建使 Flyway 在新库从零重跑，checksum 天然干净；绿地原则下 schema 按最终形态维护单一版本。配套约束：新镜像绝不能对旧库启动（runbook CD 隔离 + 构建不部署两步固化）。

备选：新增 V-next ALTER migration — 否决：为一次性重建保留演化台账没有价值。

决策 6：is_corresponding_author 恒 false

PubMed XML 无通讯作者显式标记，不做启发式推断、不造假数据；列保留，等未来更可靠数据源。

备选：从 affiliation / email 启发式识别 — 否决：准确率无保障，错标比不标更误导。

决策 7：Batch 重导解锁用 generation identifying 参数（含 attempt 规则）

Job addTimestamp=false，同参数重跑抛 JobInstanceAlreadyCompleteException。为 pubmedBaselineImportJob 增加可选 generation identifying 参数并打通 XXL→Command→Params→Port→JobParams 全链；同库失败续跑沿用同值（断点续传），换库重来必须换新值（避免旧 checkpoint 丢前半段）。

备选 A：定向删 patra_batch 元数据 — 否决：手工动共享元数据库，每次重导重来一遍。
备选 B：新建 patra_batch_v06 — 否决：整库分裂，运维面翻倍。

8. 风险与缓解

风险等级缓解
allowlist 回填漏表 / 漏行，或误拷 flyway_schema_history 带回旧 checksum high allowlist 在计划阶段逐表落名并盲核（含 flyway_schema_history 显式排除项）；恢复前目标表为空、恢复后逐表行数对照通过才放行；--single-transaction 保原子
CD 隔离遗漏或恢复时机错误，新镜像自动撞旧库 / 旧镜像覆盖新库 high disable cd.yml 是 runbook 第 2 步（合并前）、enable 是验收后最后一步；旧镜像 tag 在隔离时记录在案
回滚交换执行错误（重名冲突 / 镜像与库不配套） mid 三库名交换步骤固化进 runbook（失败库先改名带时间戳）；镜像 tag 与库版本配对记录；pg_dump 物理备份兜底
NCBI baseline 目录年度轮换导致 pubmed26n1333.xml.gz 下线 mid 重建前 HEAD 探测；下线则改用当年对应文件（数据集变化可接受，目标是修链路）
generation 使用错误（换库重来沿用旧值导致旧 checkpoint 续跑缺数据） mid attempt 规则写进 runbook 与 JavaDoc；验收第一项就是总行数对账，缺前半段立刻暴露
affiliation DAO 派生方法清理遗漏，Spring Data 启动抛 PropertyReferenceException mid 清单显式列出 DAO / IT 级联项；启动冒烟（contextLoads）+ check 门控在合并前暴露
VO Map→List 与聚合改动波及面（API 路径 converter 等调用方） low 编译期全量暴露即修；check + integrationTest 双门控兜底
作者行数量级（10 万+ 行）拖慢导入 low batchSaveWithFlush 批量写（keyword 7.5 万行同模式无压力）；离线 Job 时长非敏感
