v0.6 Catalog 作者与摘要数据链路修复

📅 2026-08-28 🌿 feat/v0.6-catalog-authors-abstracts 👤 linqibin 🎯 spec draft
关键决策摘要

v0.6 是纯后端 + 数据版本（portal 前端零改动）：① 补齐从未实现的文献作者落库三层（Processor→Writer→DAO），作者采用「行内存名 + 可空 ORCID 软关联」——关联表直接存展示名，绝不向 cat_author 新建行，作者库保持纯净；② 摘要 schema 定型为有序数组并类型化序列化（根治双重编码与读写不一致），非结构化摘要不再丢弃、结构化摘要同时生成 plain_text，两种形态一等公民；③ 修完代码后 drop patra_catalog 整库重建（直接改 V3 baseline migration），重导同一个 baseline 文件（pubmed26n1333）对齐现状，不写任何存量迁移脚本。

1. 背景与现状

mini 生产库 patra_catalog 现有 18,807 篇文献（2026-05-31 由 XXL-Job pubmedBaselineImportJob 从 NCBI 下载 pubmed26n1333.xml.gz 单文件导入），portal 文献详情页（v0.5 / PAP-45）的作者区与摘要区均为空。排查确认两条链路的缺陷：

作者：从未实现。Parser（CanonicalPublicationParsingStrategy.parseAuthorList）完整解析了 <AuthorList>（姓名 / ORCID / 机构 / EqualContrib），但 PubmedArticleItemProcessor 无 buildAuthorData()、PublicationItemWriter 无作者分支、PublicationAuthorDao 类不存在——数据解析进内存后无声丢弃。cat_publication_author 0 行；cat_author 的 49.7 万行来自另一条独立链路（authorImportJob 导入 PubMed Computed Authors 全局作者库，dev 配置限 50 万条），与文献无行级关联。项目自带的 pubmed-parsing-gap-analysis.md 早已将此标为 🔴 高优先级缺口；详情页读端 SQL 已写好 FROM cat_publication_author 在等数据。

摘要：四层缺陷叠加。① 写端把 sections 序列化为对象 {"LABEL":"text"}，读端 parseSections 期望数组 [{label,text}]——schema 从未对齐，解析失败被 catch 吞掉返回空数组（读空的主因）；② 存量 5,114 行摘要全部是双重编码的 JSON 字符串（commons Jackson3JsonFormatMapper String 透传修复前，手工 Jackson 2 序列化的字符串又被 Hibernate 二次序列化）；③ 批量路径从不生成 plain_text（API 路径的对照实现 PubmedPublicationConverter.extractAbstract 是正确的）；④ 无 Label 的非结构化摘要（PubMed 的大多数）被整条丢弃不落库——这是 27% 覆盖率（5,114/18,807）的主因，也解释了表内 100% 是 STRUCTURED。

关键前提。数据源头是可重复下载的 NCBI baseline 文件（原始采集文件未留存、ext_data 全 NULL，但不需要——重新下载即可）；portal 前端 AuthorList / AbstractBlock 组件 v0.5 已就绪，AbstractBlock 对 empty / plain / structured 三种形态的渲染逻辑齐备，API 响应契约不变则 FE 零改动。

  • ORCID 软关联：命中 cat_author_orcid 时填 author_id，未命中留空
  • 摘要 schema 定型有序数组 + Entity 字段类型化（删手工 mapToJson）
  • 非结构化摘要落库（UNSTRUCTURED）+ 结构化摘要拼接生成 plain_text
  • cat_publication_alternative_abstract 对称改造
  • 详情读端 SQL 改读行内作者名；parseSections 兜底日志 warn→error
  • mini 上 patra_catalog 整库重建 + 重导（Computed Authors + pubmed26n1333）
Out of Scope
  • Computed Authors PMID 证据关联消歧（author_id 回填留白，schema 已预留）
  • 作者检索 / 作者详情页
  • portal 前端改动（契约不变，FE 已就绪）
  • AI 速读（aiSummary 维持留空）
  • 扩大导入数据量（仍为单文件 pubmed26n1333，对齐现状）
  • authors_complete 标志改造——其语义是「PubMed 声明作者列表完整」，与 patra 是否落库无关，保持原样，仅此文档澄清语义

3. 作者落库链路

3.1 DDL（直接改 V3__create_author.sql）

cat_publication_author 改造：author_id 改 NULL（软关联位）；新增行内列 display_name VARCHAR(200) NOT NULL（"Lastname Forename" 或集体名）、last_name、fore_name、initials、collective_name、orcid VARCHAR(19)（原始 ORCID 存档，便于未来重关联 / 审计）；删除 uk_pub_author (publication_id, author_id)（author_id 大量为空后无意义），保留 uk_author_order (publication_id, author_order)。整库重建使 Flyway checksum 天然干净，无需新增 ALTER migration。

3.2 写链路（补齐三层）

  • Processor：新增 buildAuthorData()，从已解析的 publication.getAuthors() 产出——author_order 从 1 递增、is_first_author = (order==1)、is_equal_contribution 取 XML EqualContrib 标记、is_corresponding_author 恒 false（PubMed XML 无通讯作者显式标记，不造假数据）；CollectiveName 作者 display_name 存集体名、姓名各列为空。
  • ORCID 软关联：作者带 ORCID 时查 cat_author_orcid，命中填 author_id，未命中留空；绝不向 cat_author 新建行——作者库只属于 Computed Authors 导入链路，保持每行都是真正消歧过的人。批内对 ORCID→author_id 做缓存避免逐行查库。
  • Writer / Repository：中间 record（PublicationImportResult / PublicationCompleteData）增加 authors 字段；新建 PublicationAuthorDao；PublicationRepositoryAdapter.insertAllWithAssociations 增加 writeAuthorAssociations（作者行 + 机构行批量写入，机构写入 cat_publication_author_affiliation，Parser 已解析的 affiliation 数据链路打通）。

3.3 读端

PublicationDetailDao.findAuthorsByPublicationId 改读行内 pa.display_name，去掉 JOIN cat_author（行内名恒有值）；affiliation 子查询不变。API 响应字段结构不变（name / order / first / corresponding / affiliation），portal 零改动。

4. 摘要写读链路（两种形态一等公民）

4.1 写端分流

  • 结构化（XML 带 Label 分节）：sections 落有序数组，同时拼接生成 plain_text（"LABEL: text" 段落连接，规则与 PubmedPublicationConverter.extractAbstract 对照实现一致）→ ofBoth，type=STRUCTURED，两字段都有值。
  • 非结构化（无 Label 纯文本）：不再丢弃——文本落 plain_text，sections 为空 → ofPlainText，type=UNSTRUCTURED（枚举已存在）。多段无 Label 文本按段落合并。此项将摘要覆盖率从 27% 拉回预期 ≥85%（其余为真无摘要文献）。

4.2 schema 定型与类型化序列化

  • structured_sections 统一定为有序数组 [{"label","text"}]：保序（INTRODUCTION→METHODS→RESULTS→CONCLUSIONS 顺序是语义）、容纳重复 label（现 Map 形态会覆盖丢数据）。
  • Domain VO PublicationAbstract.structuredSections 从 Map<String,String> 改 List<AbstractSection>（有序 record）。
  • Entity 字段从 String + 手工 Jackson 2 序列化，改为类型化 record 列表 + @JdbcTypeCode(SqlTypes.JSON)，交给全局 Jackson3JsonFormatMapper 单点序列化；删除 PublicationJpaMapper.mapToJson（静默吞异常返 null 的源头），双重编码从机制上不可能再发生。
  • cat_publication_alternative_abstract（多语言摘要）完全对称，一并改造。

4.3 读端

读写共享同一 section record 定义，数组直接反序列化；parseSections 吞异常兜底从 log.warn 升 log.error（重建后数据格式可信，再失败即 bug，必须响；仍返回空数组保详情页可用）。plain_text 直接透传。前端 AbstractBlock 按 deriveAbstract 自动三态渲染（empty / plain / structured），无需改动。

5. 数据重建与验证

5.1 重建操作（mini，代码部署后执行）

  1. drop 并重建 patra_catalog 库 → catalog 服务重启，Flyway 全量重跑（含改过的 V3）
  2. authorImportJob 重导 Computed Authors（恢复 ~50 万作者库，dev 配置 max-records 不变）
  3. pubmedBaselineImportJob（fileIndex=1333）重导同一 baseline 文件

5.2 测试策略

  • 单测：Parser→Processor 两种摘要形态分流；buildAuthorData（普通 / 集体作者、EqualContrib、order 递增）；ORCID 命中 / 未命中软关联分支。
  • IT 补真实 round-trip：用写链路真实落库的数据喂读链路断言——当初 IT 手造数组格式测试数据、从未走真实写路径，schema 不一致因此漏网；本次两条链路必须经同一条真实路径闭环。
  • 验收（重导后 mini 实测）：curl 详情端点抽查结构化篇（sections + plainText 双非空）与非结构化篇（plainText 非空）、作者非空且顺序正确；SQL 核对摘要覆盖率 ≥85%、cat_publication_author 行数 ≈ 篇数 × 平均作者数（预估 10 万+）；portal 页面人工点开确认渲染。

6. 关键决策与备选

决策 1：存量数据清库重导，不写迁移脚本

修完代码后 drop patra_catalog 整库重建 + 重导同一 baseline 文件。源头（NCBI baseline）可重复下载，5,114 行坏格式摘要与空作者一次性全部重建，符合绿地「禁止数据迁移」原则。

备选：保留存量 + SQL 迁移修复坏摘要 + 按 PMID 补作者 — 否决：工作量更大、违反绿地原则，且数据可再生没有保留价值。

决策 2：作者采用「行内存名 + 可空 ORCID 软关联」

关联表直接存展示名（详情页 100% 有作者可显示、不依赖 join），author_id 可空、仅 ORCID 命中时填，绝不因导文献向 cat_author 新建行——作者库保持纯净（每行都是消歧过的人），作者检索能力不被重复行破坏。未来证据关联只需回填 author_id，schema 不再动。

备选 A：ORCID 匹配 + 未命中新建 cat_author — 否决：PubMed ORCID 覆盖率仅两三成，作者库会被无法消歧的重复行淹没爆炸，作者检索直接废掉（用户明确否决）。
备选 B：Computed Authors PMID 证据精确关联 — 否决（本版）：3.6GB 全量数据重导 + 证据匹配是独立大项目体量，且快照覆盖不到新文献；schema 已为其留好回填位。

决策 3：structured_sections 定型有序数组 + 类型化序列化

数组保 section 顺序、容纳重复 label；Entity 字段类型化后由全局 Jackson3JsonFormatMapper 单点序列化，读写共享同一 record 定义，schema 不一致与双重编码从机制上消除。

备选 A：保持对象形态、改读端适配对象 — 否决：Map 丢 section 顺序（顺序是语义）、重复 label 覆盖丢数据。
备选 B：保持 String 字段 + 集中手工 codec — 否决：仍是双轨序列化，静默吞异常隐患仍在。

决策 4：直接改 V3 baseline migration，不新增 ALTER migration

本次整库重建使 Flyway 从零重跑，checksum 天然干净；绿地原则下 schema 按最终形态维护单一版本。

备选：新增 V-next ALTER migration — 否决：为一次性重建保留演化台账没有价值，违背「只维护当前版本」纪律。

决策 5：is_corresponding_author 恒 false

PubMed XML 无通讯作者显式标记（通讯信息散落在 affiliation / email 中不可靠），不做启发式推断、不造假数据；列保留，等未来更可靠数据源。

备选：从 affiliation 文本 / email 启发式识别 — 否决：准确率无保障，错标比不标更误导。

7. 风险与缓解

风险等级缓解
NCBI baseline 目录年度轮换（pubmed26 → pubmed27）导致 pubmed26n1333.xml.gz 下线，重导拿不到同一文件 mid 执行重建前先 HEAD 探测文件存在性；若已下线则改用当年 baseline 对应文件（数据集变化可接受，v0.6 目标是修链路不是保数据快照）
mini 出站走代理，重下 baseline（~200MB）与 Computed Authors（3.6GB）可能慢或中断 mid Computed Authors 若 mini 本地仍有缓存文件则复用；下载中断重跑 Job 即可（Spring Batch 幂等重启）；历史上两个 Job 都在 mini 成功跑通过
整库重建误伤：patra_catalog 之外的库（batch 元数据、registry 等）被波及 low 只 drop/create patra_catalog 单库；patra_batch 元数据库不动（旧 job 实例参数留档无害）
VO Map→List 改动波及面：PublicationAbstract 的现有调用方（API 路径 converter 等）编译期暴露 low 编译期全量暴露即修；./gradlew check 全栈门控兜底
作者行数量级（10 万+ 行 / 批 500 篇 chunk）拖慢导入 low 沿用现有 batchSaveWithFlush 批量写模式（keyword 7.5 万行同模式无压力）；导入是离线 Job，时长非敏感
