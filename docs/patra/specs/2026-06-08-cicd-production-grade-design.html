CI/CD 生产级优化：受影响单元门控 + 治理硬化

📅 2026-06-08（rev 06-09 纳入对抗式 review） 🌿 feat/cicd-production-overhaul 👤 linqibin 🎯 spec draft
关键决策摘要

把后端 CI 从「前端改动也触发后端全套、4 个 shard 永远全跑」重构为「统一编排 + 受影响单元门控」：一个 detect-changes 决策、一个 required-check 总 gate，按受影响单元（service / contract / foundation / portal）精确门控 unit / slice / integration / e2e。关键修正：运行时测试虽无多服务拓扑，但编译期 API 契约存在跨服务消费者（如 registry-api 被 catalog / ingest / expr-starter 依赖），路由必须把契约变更扇出到消费者服务，扇出关系派生自真实 Gradle 模块依赖图，未确定即保守 full-run。foundation 变更全跑、nightly cron 全量兜底。配套：CodeRabbit 关增量复评（复评改由 Claude 分批 @ 触发）、两层 Gradle 缓存且仅 trusted CI 可写远程缓存、前端 / Docker 层缓存、pin action SHA + 最小 permissions + Dependabot。AI review 治理：CodeRabbit 配置 best-practice 化 + 刚合并的 Claude review 加固，双 reviewer 分工（CodeRabbit 广度 / Claude 深度）、各 PR 只评一次。顺手修复「前端质量门未进分支保护 → 前端 lint/test 拦不住合并」与「选择性运行下 coverage 聚合语义不成立」两个隐患。分支保护配置零改动。

1. 背景与现状

最近 #140–147 已建成后端多服务 CD：patra-infra/cd/detect-changes.sh + services.json 作为 SSOT 路由出受影响服务 → 动态 matrix 并行 bootJar+docker build 推 GHCR → Mac mini self-hosted runner 部署；Spring Boot 4 分层 jar 让弱网部署只传 ~487KB application 层。CD 侧选择性构建已达标，本次不动它。问题集中在 CI 侧（ci.yml / ci-docs.yml / portal-ci.yml）：

  1. CodeRabbit rate limit：.coderabbit.yaml 显式设 auto_pause_after_reviewed_commits: 0（注释写明「保证每次 push 增量审查」）——配置意图就是每 push 必复评，叠加 TDD 多碎 commit + 反复 push，配额必然打爆。
  2. 前后端未隔离 + 前端门失守：ci.yml 的 paths-ignore 只排 docs/**，没排 patra-portal/**——只改前端也跑后端全套；且分支保护只 require required-check，portal-ci-required-check 未进 required 列表，前端 lint/typecheck/test 失败拦不住合并。
  3. 测试全量重跑：后端 unit-tests 固定 4-shard matrix 永远全跑；integration / e2e 各一个 job 也全跑。改 catalog 一个文件，registry / ingest / commons 全部陪跑。
  4. 隐患 · 供应链：所有 action pin 到可变 tag @vX（非 SHA）。公开仓库——2025 年 tj-actions 投毒波及 2.3 万仓库。
  5. 隐患 · 缓存：CD 的 docker build 无 buildx 层缓存；portal-ci 无 .next/cache 缓存。
  6. 新增 · 双 AI reviewer：刚合并的 claude-code-review.yml（#148）让 Claude 也自动 review PR，与 CodeRabbit 形成两个自动 reviewer；但其 permissions: pull-requests: read 发不了评论（静默失败）、触发含 synchronize（每 push 重跑）、action 未 pin SHA。CodeRabbit 现配置「只跑通」，多项最佳实践未拧紧（见 §5）。

2. 范围边界

In Scope
  • 后端 CI 重构为单一编排 workflow：detect-changes → 受影响单元 matrix → required-check 总 gate。
  • 受影响单元门控（service / contract / foundation / portal）；contract 变更扇出到消费者服务（派生自 Gradle 依赖图）；foundation 全跑；nightly cron 全量兜底。
  • 明确 detect-changes 输出模型、PR 的 base/head diff 模式、空 matrix 与 skipped job 的 Actions 语义、required-check 的 success/skipped 判定。
  • 前端检查并入统一编排（含非阻塞 Playwright e2e 信号），修复 portal 质量门未被 require 的 bug。
  • 修正选择性运行下的 coverage 语义（PR 选择性 ≠ 全仓聚合）。
  • 提取镜像版本一致性 preflight job，避免选择性跑漏掉这条 cheap governance。
  • 删除 ci-docs.yml、portal-ci.yml。
  • AI review 治理：CodeRabbit best-practice overhaul（关增量复评 + 吃进 .claude/rules 规约 + fbinfer/安全工具 + 降噪 + 分层 path_instructions）；Claude review 工作流加固（修 permissions、每 PR 评一次、author 门控、pin SHA）；双 reviewer 分工；复评由 Claude @ 驱动；更新评审流程文档。
  • 两层 Gradle 缓存（GHA + Mac mini node，信任边界：仅 trusted CI 可写）、portal .next/cache、CD buildx 层缓存。
  • 全 workflow pin commit SHA（格式 @<sha> # vX.Y.Z）、最小 permissions:、新增 .github/dependabot.yml。
  • detect-changes 路由的 TDD 测试。
Out of Scope
  • 不动 CD 部署逻辑本身（cd.yml deploy job、compose、分层 jar）——已达标。
  • 不引入 Develocity Predictive Test Selection（单人 + 私有 + 无历史，过度工程）。
  • 不引入 Bazel / Nx / AffectedModuleDetector（只对 contract 用轻量图派生，不上通用 AMD 引擎）。
  • 不做跨服务运行时 e2e（当前无；将来真有了再单列一档）。
  • 不改 GitHub 分支保护设置（required-check 名称不变）。
  • Mac mini 网络层修复由用户处理，非本 PR 的工程范围。

3. CI 编排与 gate 语义

现状结构性问题：三个 workflow + 两个 gate 名互补拼凑——ci.yml（除 docs 外什么都触发，含前端）+ ci-docs.yml（docs-only 兜底）+ portal-ci.yml（产出 portal-ci-required-check，但没进保护）。漏了前端隔离，前端门形同虚设。

目标结构：合并成一个编排 workflow，一个 detect-changes 决策、一个 required-check 总 gate（分支保护那条 required-check 名称不动）：

ci.yml  (on: pull_request + push:main + schedule[nightly])
└─ detect-changes ──► 输出: backend_units_json, portal_changed, docs_only, full_run(+reason), coverage_mode
   ├─ preflight     镜像版本一致性守卫（cheap，常驻跑）
   ├─ backend  [matrix: backend_units_json]   仅当 != '[]'：每个受影响单元一个 job
   │                 ./gradlew :<unit 模块…>:check :…:integrationTest :…:e2eTest（有啥跑啥）
   ├─ portal   if portal_changed：blocking lint/typecheck/test + 非阻塞 Playwright e2e
   ├─ coverage if coverage_mode != none：按模式上传（见 §4）
   └─ required-check  (if: always, needs: 全部)  ← 唯一 required，真覆盖前后端

3.1 detect-changes 输出模型与触发模式

把现有 detect-changes.sh（仅 push <before> <after> / dispatch）扩展为显式模式，并产出结构化输出，避免「一个 units[] 打天下」：

  • 模式：push <before> <after>（push:main）、pr <base_sha> <head_sha>（pull_request，checkout 用 fetch-depth: 0 并以 merge-base 求 diff）、dispatch <service|all>（保留 CD 手动）、schedule（直接 full）。
  • 输出：backend_units_json（受影响后端单元数组）、portal_changed（bool）、docs_only（bool）、full_run+full_run_reason、coverage_mode（none / flags / full）。

3.2 Gate 语义（明确写死）

  • required-check：当所有 required 依赖结果 ∈ {success, skipped} 即绿；任一 failure 或 cancelled 即红。docs-only / portal-only 下后端与 coverage 为 skipped，gate 仍能正确判定。
  • 空 matrix 防护：backend job 用 if: needs.detect-changes.outputs.backend_units_json != '[]' 包住，避免空 matrix 生成非法 workflow。
  • preflight：把 ci.yml 现有的 POSTGRES_IMAGE/ROCKETMQ_IMAGE 与 Java 常量、compose 文件一致性守卫提成独立 cheap job，常驻跑（或至少在 workflow / starter-test / compose / full-run 时跑），不随服务门控被漏掉。
  • 删 ci-docs.yml / portal-ci.yml：docs-only 由统一 gate「无失败即绿」取代；portal 检查并入主编排后 required-check 真正覆盖前端。CD 侧（cd.yml / portal-cd.yml）保持独立。

4. 受影响单元门控与测试矩阵

4.1 受影响单元模型（替代「服务目录」）

门控单位不是「改了哪个目录」，而是「受影响的单元」，分四类：

  • service：服务私有实现（domain / app / infra / adapter / boot，以及无跨服务消费者的 api，如 catalog-api / ingest-api）→ 只跑所属服务。
  • contract：被别的服务编译期依赖的 api 模块 → 触发该服务 + 所有消费者服务。当前真实契约边（grep 自 build.gradle.kts）：
    • patra-registry-api/** → registry + catalog + ingest + expr-starter（及 expr-starter 的下游消费者）
    • patra-object-storage-api/** → object-storage + ingest
  • foundation：全仓共享基础设施 → full-run（全部后端单元）。清单见 §4.4。
  • portal：前端独立单元。
契约扇出的来源：派生，不手维护

消费者集派生自真实 Gradle 模块依赖图（SSOT = 实际 build.gradle.kts），而非手写映射——避免与代码漂移。保守兜底：任何 api / 共享 / 未识别路径在无法确定消费者集时一律 full-run（只会过度运行、绝不漏运行）。且 build.gradle.kts 本身变更属 foundation → full-run，因此依赖图「陈旧」是自我纠正的。具体机制（build-logic 任务生成 reverse-dep 映射并 checked-in + staleness 守卫 vs detect-changes 内实时计算）在实现计划定。

4.2 为什么必须有 contract 这一档

原设计「命中服务目录就只跑该服务」会漏测跨服务消费者：只改 registry-api 而只跑 registry，会漏掉 catalog-infra / ingest-infra / expr-starter 的编译与测试。这不是「未来新增跨服务测试」的隐患，而是当前仓库已存在的编译期契约依赖。运行时测试无多服务拓扑（见 §4.3）≠ 编译期模块隔离。

4.3 测试本身可按单元选择性执行（运行时依据）

调查证实：Patra 后端 integrationTest 几乎全是 Spring slice（@DataJpaTest×27、@WebMvcTest×5、@WireMockTest×1、最小 @SpringBootTest(classes=Job)×4），运行时不启动多服务拓扑：唯一调 registry 的 DictionaryResolverAdapterIT 用 WireMock stub 掉 registry。e2e 仅 catalog-boot×2，只起 catalog 自身上下文、@MockitoBean 屏蔽外部 I/O。各服务 IT 用独立容器独立库名（withReuse(false)）。→ 运行时测试可按受影响单元选择性执行；但路由必须叠加 §4.1 的 contract 扇出来覆盖编译期消费者。

档Gradle 源集门控粒度PR / push:mainnightly cron
unit（纯 Java）test（经 check）按受影响单元仅受影响单元全量
slice + integrationintegrationTest按受影响单元仅受影响单元全量
e2e（单服务全上下文）e2eTest按受影响单元仅受影响单元全量
前端 blockingpnpm lint/typecheck/testportal 单元仅 portal 受影响全量
前端 e2e（Playwright）pnpm test:e2eportal 单元PR 非阻塞（传报告）阻塞（UI 回归兜底）
contract（跨服务 api）—扇出消费者服务该服务 + 消费者全量
foundationcommon / starter / build-logic / 根构建扇出全部全跑全跑

为何门控才是省时杠杆（不是缓存）：Testcontainers 测试因随机端口等 volatile 输入，Gradle build cache 的 FROM-CACHE 基本不成立（Gradle issue #9151），CI 全新 runner 上 UP-TO-DATE 也帮不上。所以对 IT 唯一能省时间的，是压根不启动未受影响单元的 integrationTest——正是单元门控做的事。unit/slice 的 test 任务则可正常 FROM-CACHE。

4.4 coverage 语义（选择性 ≠ 全仓）

根 build.gradle.kts 用 jacoco-report-aggregation 把所有 apply jacoco 的子项目纳入聚合。选择性只跑 catalog 时，全仓聚合会把未运行模块算成 0 覆盖或产出残报告；portal-only / docs-only 时根本没有 jacoco-exec-* artifact。codecov-action 又是 fail_ci_if_error: true。规则：

  • coverage_mode = full（foundation / full-run / nightly）：跑全仓聚合并上传全量 coverage。
  • coverage_mode = flags（服务级 PR）：只上传受影响单元的 coverage，用 Codecov flags 区分 catalog / registry / ingest 等，不伪装成全仓。
  • coverage_mode = none（docs-only / portal-only）：后端 coverage job skipped，required-check 接受 skipped。
foundation 单元的扇出清单

patra-common-model / patra-common-enums / patra-common-provenance-api（Shared Kernel）、linqibin-commons-*、patra-spring-boot-starter-*、patra-expr-kernel、build-logic/、根 build.gradle.kts / settings.gradle.kts / gradle.properties、gradle/、service.Dockerfile、docker-compose.apps.yaml、patra-infra/cd/*（路由 SSOT 自身）、.github/workflows/** —— 任一变更即 full-run（workflow 变更额外触发 portal，以验证整条新管线）。

5. AI Review 治理（CodeRabbit + Claude Code）

仓库现有两个 AI reviewer：CodeRabbit + 新加的 Claude Code（claude.yml 的 @claude 交互 + claude-code-review.yml 的 PR 自动 review）。实测两者 findings ~93% 不重叠，定位为互补、分工，不是竞争：

5.1 双 reviewer 分工 + 各 PR 评一次

  • CodeRabbit = 广度：行级 nitpick + lint/安全工具聚合（shellcheck / hadolint / actionlint / gitleaks / …）+ 跨文件一致性 + Linear AC 对齐 + area 标签。
  • Claude = 深度：六边形架构纯净性、DDD 领域模型、跨服务契约、复杂重构意图。
  • 两者都「每 PR 评一次」：CodeRabbit auto_incremental_review: false；Claude review 触发改 [opened, ready_for_review]、去掉 synchronize（不再每 push 重跑）。复评由 Claude 分批 @coderabbitai review / @claude 手动触发，用户不参与。Monitor 覆盖三条流（CodeRabbit + Claude review + 人工）。

5.2 CodeRabbit 配置 overhaul（现「只跑通」，本次拧紧）

  • rate limit：auto_incremental_review: false，删 auto_pause_after_reviewed_commits: 0 并同步改注释（去掉「保证每次 push 增量审查」反向说明）。论据基于当前配置意图（显式 :0 + 注释），不押 SaaS 默认值。保留 enabled: true + drafts: false（ready 首评兜底）。
  • 吃进项目规约：knowledge_base.code_guidelines.filePatterns: [".claude/rules/**/*.md"]——现配置读不到 port-service.md / error-handling.md / code-style.md（CLAUDE.md 已默认吸收）。
  • Java bug 检测：fbinfer.enable_java: true（默认 false，Java 项目不开等于没有）。
  • 安全工具显式声明：trufflehog / checkov / trivy / osv_scanner / zizmor / opengrep（公开仓库基线）；关 pmd / semgrep / biome 等重复或无关项。
  • path_instructions：前端 {ts,tsx} 花括号 glob 拆两条（否则 tsx 可能没匹配上）；新增 patra-common-* / patra-spring-boot-starter-* 全局影响模块专项；各层标注「【让给 Claude】架构深评 /【不要评论】框架约定写法」以免与 Claude 叠加。
  • 降噪：关 changed_files_summary / related_issues / related_prs。
  • （可选）TDD 预合并检查：pre_merge_checks 自定义 check（warning 级，不阻断——与 request_changes_workflow: false 一致），提示「production 变更须伴随测试变更」。

5.3 Claude review 工作流加固

  • claude-code-review.yml：修 permissions: pull-requests: write（现 read，发不了评论、静默失败）；触发改 [opened, ready_for_review]；author 门控（仅 owner PR，防 prompt injection + 省 OAuth 额度）；use_sticky_comment: true；claude_args: --max-turns N 限深；pin SHA。
  • claude.yml：pin SHA、按需 pull-requests: write、author 门控。
  • 安全：保持 pull_request（非 pull_request_target）——fork 拿不到 secret，安全。
  • 固化进规则：更新根 CLAUDE.md「PR 与代码评审」节（复评由 Claude 分批 @ 触发、开发期 draft 降频、Monitor 覆盖三条 review 流）。

6. 缓存策略与信任边界

fail-soft 解决可用性，trust 边界解决正确性——两件事分开。

  • Gradle 第一层 · GHA 缓存：维持 gradle/actions/setup-gradle，PR 只读、main / nightly 写。与 runner 同地、最快、始终可用。
  • Gradle 第二层 · Mac mini build-cache-node：在 patra-infra compose 起 gradle/build-cache-node（鉴权 + 持久卷），价值是持久化、突破 GHA 10GB 上限的 CI 缓存。信任边界（生产级默认）：
    • 写入者仅限 trusted CI：push:main、schedule、手动 trusted dispatch。PR 默认只读。
    • 本地开发默认不 push 到 CI 信任缓存（不干净/非 hermetic 环境写入会让 CI 复用错误产物 → false-pass）。如需本地远程缓存，用独立 namespace / 独立 node，不与 CI trusted cache 混用。
    • fork PR 或 secrets 缺失时完全禁用远程缓存（拿不到 tailnet / 凭据），只保留 GHA / 依赖缓存；远程缓存 fail-soft，node 不可达只是 cache miss、绝不阻断 CI。
    • 凭据只走 GitHub Secrets / 本机外部 secret，绝不写入仓库 .env。
  • 前端：portal job 加 actions/cache 缓存 .next/cache（key = lockfile + 源码 hash）；pnpm 缓存已有。
  • CD docker build：接 buildx cache-from/cache-to=type=registry,mode=max，让分层 jar 的 dependencies 层不再每次从零重建。

7. 安全加固（公开仓库生产级）

  • 所有 action pin 到 commit SHA，格式统一 uses: owner/action@<sha> # vX.Y.Z。公开仓库 post-tj-actions 硬标准。
  • 最小 permissions:：workflow 顶层默认 contents: read，仅需要处 job 级提权（CD 推 GHCR 才 packages: write）。
  • 新增 .github/dependabot.yml：托管 github-actions（升 SHA）、gradle、pnpm 三生态，按周分组降噪。注意：分组 PR 仍需人工审 action 权限变化，不能只看 SHA diff。bot PR 已被 coderabbit ignore_usernames 排除，不加重 rate limit。（Renovate 更强但需装 App，对单人徒增装配，选原生 Dependabot。）

关键决策与备选

决策 1：受影响单元门控 + 契约消费者扇出（派生自依赖图）

门控单位为「受影响单元」（service / contract / foundation / portal）。contract（跨服务 api）变更扇出到消费者服务，扇出关系派生自真实 Gradle 模块依赖图，未确定即保守 full-run。

备选 A：按服务目录门控（原设计）— 否决：当前已存在编译期 API 契约依赖（registry-api→catalog/ingest/expr-starter 等），只跑所属服务会漏测消费者。
备选 B：手维护 contracts 映射 — 否决：会与真实 build.gradle.kts 漂移；改用图派生 + full-run 兜底。
备选 C：完整通用 AMD 引擎 — 否决：只有 contract 需要依赖图，轻量派生足矣。

决策 2：integration / e2e 按单元门控（运行时无多服务拓扑）

测试运行时不启动多服务拓扑（跨服务交互被 WireMock / @MockitoBean 隔离），故可按受影响单元选择性执行；编译期契约由决策 1 的 contract 扇出覆盖。

备选：integration/e2e 任一后端变更就全跑 — 否决：数据不支持，违背痛点初衷。兜底：nightly 全量 + 「未来新增跨服务运行时测试时单列 e2e 档」的不变量约定。

决策 3：统一编排 + 单一 required-check gate（含显式语义）

一个 detect-changes + 一个 if: always() 总 gate（名仍 required-check）：所有 required 依赖 ∈ {success, skipped} 即绿，任一 failure/cancelled 即红；空 matrix 用 if backend_units_json != '[]' 防护。分支保护零改动，且首次真正覆盖前端门。

备选 A：保留多 workflow + 多互补 gate（现状）— 否决：拼凑脆弱、漏前端隔离、portal gate 未进保护。
备选 B：on.paths workflow 级过滤 + 设 required — 否决：skipped 的 required check 让 PR 永久 pending。

决策 4：CodeRabbit 关增量复评 + Claude 分批 @ 驱动

auto_incremental_review: false，保留 ready 首评；复评由 Claude 处理完一批反馈后 @coderabbitai review 触发，用户不参与。论据基于当前配置意图（显式 :0 + 注释），不押 SaaS 默认值。

备选 A：保留增量、靠 draft/squash 纪律降频 — 否决：依赖每次自觉。
备选 B：auto_pause_after_reviewed_commits: 3 — 否决：每 PR 仍先耗 3 次配额。

决策 5：两层缓存 + 严格信任边界

GHA 缓存（CI↔CI）+ Mac mini 远程 node（持久化、突破 10GB）。仅 trusted CI（push:main/nightly）可写远程缓存，PR 只读，本地 dev 不混用 CI trusted cache，fork/缺 secret 时禁用远程缓存。fail-soft 仅解决可用性、不解决信任。

备选 A：本地 dev push=true、PR 复用本地产物（原设计）— 否决：不干净本地环境污染 CI 信任缓存 → false-pass。
备选 B：仅 GHA 缓存、不要 node — 用户决策保留 node；网络由用户修复。

决策 6：Dependabot（而非 Renovate / 手动）

原生、零 App 装配，.github/dependabot.yml 托管 actions(SHA)/gradle/pnpm，按周分组；分组 PR 仍人工审权限变化。

备选 A：Renovate — 否决：需装 GitHub App，对单人徒增装配。
备选 B：手动升级 — 否决：pin SHA 后不托管会滞后腐化。

决策 7：不上 Develocity Predictive Test Selection

PTS 需 ≥14 天历史 + 50+ 次执行冷启动、私有商业项目无免费层。单人 + 私有 + 无历史三条全不满足。单元门控 + build cache 已覆盖收益。

否决理由：当前阶段过度工程。

决策 8：选择性 coverage 不伪装成全仓

PR 服务级用 Codecov flags 上传受影响单元 coverage；foundation/full/nightly 出全仓聚合；docs-only/portal-only coverage skipped、gate 接受 skipped。

备选：选择性跑仍走 jacoco-report-aggregation 全仓上传 — 否决：未运行模块被算 0 覆盖、产残报告，fail_ci_if_error 还可能误红。

决策 9：双 AI reviewer 分工 + 每 PR 评一次

CodeRabbit 走广度（工具聚合 + 行级 + Linear AC），Claude 走深度（架构 + 领域逻辑），实测 ~93% 非重叠；两者均改「每 PR 评一次」（去每 push 复评），复评手动 @。CodeRabbit 同步做 best-practice overhaul，Claude review 修 permissions + author 门控 + pin SHA。

备选 A：只留一个自动 reviewer（Claude 仅 @mention）— 用户决策保留双 reviewer 的互补价值。
备选 B：两个都保留每 push 复评 — 否决：噪音 / 额度叠加，违背本次降噪初衷。
