CI/CD 生产级优化：变更感知门控 + 治理硬化

📅 2026-06-08 🌿 feat/cicd-production-overhaul 👤 linqibin 🎯 spec draft
关键决策摘要

把后端 CI 从「前端改动也触发后端全套、4 个 shard 永远全跑」重构为「统一编排 + 变更感知门控」：一个 detect-changes 决策、一个 required-check 总 gate，按受影响服务精确门控 unit / slice / integration / e2e（调查证实 Patra 测试零跨服务，可安全按服务门控），foundation 模块变更才扇出全跑，nightly cron 跑全量做安全网。同时根治 CodeRabbit rate limit（关增量复评、复评改由 Claude 分批 @coderabbitai review 触发）、补齐两层 Gradle 缓存与前端 / Docker 层缓存、按公开仓库生产标准 pin action 到 SHA + 最小 permissions + Dependabot 托管。顺手修复「前端质量门 portal-ci-required-check 未进分支保护 → 前端 lint/test 拦不住合并」的隐藏 bug。分支保护配置零改动。

1. 背景与现状

最近 #140–144 已建成后端多服务 CD：patra-infra/cd/detect-changes.sh + services.json 作为 SSOT 路由出受影响服务 → 动态 matrix 并行 bootJar+docker build 推 GHCR → Mac mini self-hosted runner 按依赖顺序 compose pull/up + 健康检查；Spring Boot 4 分层 jar 让弱网部署只传 ~487KB 的 application 层。CD 侧的选择性构建已经达标，本次不动它。

问题集中在 CI 侧（ci.yml / ci-docs.yml / portal-ci.yml）——三个痛点 + 三个隐患：

  1. CodeRabbit rate limit：.coderabbit.yaml 未设 auto_incremental_review（默认 true，每次 push 增量复评），且把 auto_pause_after_reviewed_commits 显式设为 0（关掉了「复评 N 次后暂停」的安全阀）。TDD 多碎 commit + 一个 PR 内反复 push → 配额必然打爆。
  2. 前后端未隔离：ci.yml 的 paths-ignore 只排除 docs/**、*.md，没排除 patra-portal/**——只改前端，整套后端 CI（4 个测试 shard + 集成 + e2e）照样全跑。更隐蔽的是：分支保护只 require 了 required-check（后端 CI 产出的），portal-ci-required-check 根本没进 required 列表，前端 lint/typecheck/test 失败其实拦不住合并。
  3. 测试全量重跑：后端 unit-tests 是固定 4-shard matrix（commons / registry / ingest / catalog-and-misc），永远全跑；integration-tests / e2e-tests 各一个 job 也全量跑。改 catalog 一个文件，registry / ingest / commons 全部陪跑。
  4. 隐患 · 供应链：所有 action pin 到可变 tag @vX（非 commit SHA）。本仓库是公开仓库——2025 年 tj-actions/changed-files 投毒波及 2.3 万仓库、泄露 secrets。
  5. 隐患 · 构建缓存：CD 的 docker build 未接 buildx 层缓存，每次从零重建镜像层。
  6. 隐患 · 前端缓存：portal-ci 未缓存 Next.js .next/cache。

2. 范围边界

In Scope
  • 后端 CI 重构为单一编排 workflow：detect-changes → 受影响服务 matrix → required-check 总 gate。
  • unit / slice / integration / e2e 按受影响服务门控；foundation 变更扇出全跑；nightly cron 全量兜底。
  • 前端检查并入统一编排，修复 portal 质量门未被 require 的 bug。
  • 删除 ci-docs.yml、portal-ci.yml。
  • CodeRabbit：关增量复评、复评改由 Claude @ 驱动、更新评审流程文档。
  • 两层 Gradle 缓存（GHA + Mac mini build-cache-node）、portal .next/cache、CD buildx 层缓存。
  • 全 workflow pin commit SHA、最小 permissions:、新增 .github/dependabot.yml。
  • detect-changes 路由的 TDD 测试。
Out of Scope
  • 不动 CD 部署逻辑本身（cd.yml deploy job、compose、分层 jar）——已达标。
  • 不引入 Develocity Predictive Test Selection（单人 + 私有 + 无历史，过度工程）。
  • 不引入 Bazel / Nx / AffectedModuleDetector。
  • 不做跨服务 e2e（当前代码库零跨服务测试；将来真有了再单列一档）。
  • 不改 GitHub 分支保护设置（required-check 名称不变）。
  • Mac mini 网络层修复由用户处理，非本 PR 的工程范围。

3. CI 编排重构（统一 gate + 变更感知）

现状结构性问题：三个 workflow + 两个 gate 名互补拼凑——ci.yml（除 docs 外什么都触发，含前端）+ ci-docs.yml（docs-only 兜底 gate）+ portal-ci.yml（产出 portal-ci-required-check，但没进分支保护）。漏了前端隔离，前端质量门形同虚设。

目标结构：合并成一个编排 workflow，一个 detect-changes 决策、一个 required-check 总 gate（分支保护那条 required-check 不用动）：

ci.yml  (on: pull_request + push:main + schedule[nightly])
└─ detect-changes ──────────► 输出: units[]（每服务一单元 + foundation 单元）, portal?, only_docs?
   │   复用并扩展 patra-infra/cd 的路由 SSOT；
   │   foundation / .github/workflows/** 变更 或 event=schedule → units = 全部
   ├─ backend  [matrix: units]   每个受影响服务一个 job：
   │                             ./gradlew :<svc>…:check :…:integrationTest :…:e2eTest（有啥跑啥）
   ├─ portal   (lint/typecheck/test)   if portal 受影响
   ├─ coverage  聚合实际跑过的 jacoco
   └─ required-check  (if: always, needs: 全部)  ← 唯一 required，真覆盖前后端
  • 单元粒度：matrix 的单位是「服务」（registry / ingest / catalog / object-storage / gateway）+ 一个「foundation」单元。每个 backend job 跑该服务自己的 check（unit + spotbugs + spotless）+ integrationTest（slice + Testcontainers）+ e2eTest（若有）。
  • 正确性扇出：foundation 模块（common / starter / build-logic / 根构建 / gradle/ / 共享 Dockerfile / compose）或 .github/workflows/** 变更 → units 展开为全部服务（CI 自身改动强制全跑以验证新管线）。保守 fallback：未识别路径一律全跑。
  • nightly cron：event=schedule 时 detect-changes 直接返回全部单元，跑全量 check + integrationTest + e2eTest + 前端——既是漏测安全网，也把 Gradle 缓存喂满，给白天 PR 提速。
  • 删 ci-docs.yml / portal-ci.yml：docs-only PR 时所有真实 job 跳过，required-check 判「无失败即绿」，不再需要单独兜底 workflow；portal 检查并入主编排后，required-check 从此真正覆盖前端。CD 侧（cd.yml / portal-cd.yml）保持独立，部署生命周期不同。

4. 测试门控矩阵

调查依据（关键）：Patra 后端 integrationTest 几乎全是 Spring slice 测试——@DataJpaTest×27、@WebMvcTest×5、@WireMockTest×1、最小化 @SpringBootTest(classes=SomeJob.class)×4，且 零跨服务：唯一看着跨服务的 DictionaryResolverAdapterIT（catalog 调 registry）用 WireMock stub 掉了 registry，自包含在 catalog-infra。e2e 仅 catalog-boot 两个，@SpringBootTest 只起 catalog 自身上下文、@MockitoBean 屏蔽文件下载/MinIO/Nacos，不启动任何别的服务。各服务 IT 用独立容器、独立库名（patra_catalog/patra_registry/patra_ingest，withReuse(false)）。→ integration 与 e2e 都能安全按服务门控。

档Gradle 源集门控粒度PR / push:mainnightly cron
unit（纯 Java）test（经 check）按服务仅受影响服务全量
slice + integrationintegrationTest按服务仅受影响服务全量
e2e（单服务全上下文）e2eTest按服务仅受影响服务全量
前端pnpm独立单元仅 portal 受影响全量
foundation 变更common / starter / build-logic / 根构建扇出全部服务全跑全跑

为何门控才是省时杠杆（不是缓存）：Testcontainers 测试因随机端口等 volatile 输入，Gradle build cache 的 FROM-CACHE 基本不成立（Gradle issue #9151）；CI 在全新 runner 上 UP-TO-DATE 也帮不上。所以对 IT 唯一能省时间的，就是压根不启动未受影响服务的 integrationTest——正是服务级门控做的事。unit/slice 的 test 任务则可正常 FROM-CACHE。

foundation 单元的扇出清单

linqibin-commons-*、patra-spring-boot-starter-*、patra-common-model / patra-common-enums / patra-common-provenance-api（Shared Kernel）、patra-expr-kernel、build-logic/、根 build.gradle.kts / settings.gradle.kts / gradle.properties、gradle/、service.Dockerfile、docker-compose.apps.yaml、.github/workflows/** —— 任一变更即全跑。

5. CodeRabbit rate limit 治理

  • .coderabbit.yaml 改一处：auto_review.auto_incremental_review: false（push 不再自动增量复评——根治点）。保留 enabled: true + drafts: false（PR 转 ready 时仍自动首评兜底）。删掉随之失效的 auto_pause_after_reviewed_commits: 0 避免误导。
  • 复评由 Claude 驱动：开发期 PR 挂 draft（不评）→ 完工转 ready（自动首评）→ Claude 处理完一批反馈、推送后在评论区发 @coderabbitai review 触发复评。用户全程不参与触发。
  • 固化进规则：更新根 CLAUDE.md「PR 与代码评审」节——「复评由 Claude 分批 @ 触发、开发期保持 draft 降频」，并接上既有的「开 PR 后必启 Monitor」规则（Monitor 跟踪评论流不变，只是复评变手动触发）。

6. 缓存策略（两层 Gradle + 前端 + Docker）

  • Gradle 第一层 · GHA 缓存：维持 gradle/actions/setup-gradle，PR 只读、main / nightly 写。与 runner 同地、最快、始终可用。
  • Gradle 第二层 · Mac mini build-cache-node：在 patra-infra compose 起一个 gradle/build-cache-node 容器（带鉴权 + 持久卷），桥接本地开发 ↔ CI——本地 TDD 跑完测试推上去，CI 的 PR 直接命中刚算好的产物，且不受 GHA 10GB 上限约束。settings.gradle.kts 配 HttpBuildCache：本地 dev 与 CI main/nightly push=true、PR 只读。CI 经 tailnet 访问该 node；Gradle 远程缓存 fail-soft——node 不可达只是缓存未命中、绝不让 CI 失败，第一层 GHA 缓存兜底。Networking 细节留给实现计划与用户的网络修复对接。
  • 前端：portal job 加 actions/cache 缓存 .next/cache（key = lockfile + 源码 hash）；pnpm 缓存已有。
  • CD docker build：接 buildx cache-from/cache-to=type=registry,mode=max，让分层 jar 的 dependencies 层不再每次从零重建（push 因 GHCR 去重本就小，省的是构建时间）。

7. 安全加固（公开仓库生产级）

  • 所有 action pin 到 commit SHA（带 # vX.Y.Z 注释）。公开仓库 post-tj-actions 的硬标准。
  • 最小 permissions:：workflow 顶层默认 contents: read，仅在需要处 job 级提权（CD 推 GHCR 才 packages: write，deploy 才 packages: read）。
  • 新增 .github/dependabot.yml：托管 github-actions（自动升 SHA）、gradle、pnpm 三个生态，按周分组提 PR 降噪。bot PR 已被 coderabbit ignore_usernames 排除，不会加重 rate limit。（更强的 Renovate 需装 GitHub App，对单人徒增装配，故选原生 Dependabot。）

关键决策与备选

决策 1：变更感知的服务级门控 + Gradle 构建缓存

复用 CD 的 detect-changes SSOT 驱动 CI，按变更落到的服务只跑对应 job；服务内部靠 build cache 跳过未变 task。微服务间互不依赖内部实现（跨服务走 API/事件契约），服务级隔离安全。

备选 A：纯 Gradle 构建缓存、不做门控 — 否决：4 个 shard 仍全部启动，没真正消除「无关服务陆跑」的观感与固定 runner 开销。
备选 B：完整依赖图 affected detection — 否决：对单人项目是过度工程，需额外工具/脚本维护依赖图。

决策 2：integration / e2e 也按服务门控（而非粗粒度全跑）

调查证实 Patra 的 IT 几乎全是 slice、且零跨服务（跨服务交互均被 WireMock/@MockitoBean 隔离在单服务边界内），各服务独立容器独立库名。因此 integration 与 e2e 可与 unit 同档按服务门控。

备选 A：integration/e2e 任一后端变更就全跑 — 否决：数据不支持，会让改 catalog 仍陪跑 registry/ingest 的 IT，违背痛点初衷。
兜底：nightly cron 全量 + 「未来新增跨服务测试时同步更新门控/单列 e2e 档」的不变量约定。

决策 3：统一编排 + 单一 required-check gate

一个 detect-changes + 一个 if: always() 的总 gate（名仍为 required-check），下游 backend/portal job 随意跳过。分支保护只认 required-check，配置零改动，且首次真正覆盖前端质量门。

备选 A：保留多 workflow + 多互补 gate（现状）— 否决：拼凑脆弱、漏了前端隔离、portal gate 没进保护形同虚设。
备选 B：用 on.paths 在 workflow 级过滤 + 设 required — 否决：skipped 的 required check 会让 PR 永久卡 pending。

决策 4：CodeRabbit 关增量复评 + Claude 分批 @ 驱动

auto_incremental_review: false，保留 ready 首评；复评由 Claude 处理完一批反馈后 @coderabbitai review 触发，用户不参与。

备选 A：保留增量、靠 draft/squash 纪律降频 — 否决：依赖每次自觉，偶尔忘了又打爆。
备选 B：auto_pause_after_reviewed_commits: 3 — 否决：每个 PR 仍先消耗 3 次配额，半吊子。

决策 5：两层缓存含 Mac mini build-cache-node

GHA 缓存（CI↔CI）+ Mac mini 远程 node（桥接本地↔CI、突破 10GB 上限）。远程缓存 fail-soft，node 下线退化为缓存未命中、不阻断 CI。

备选：仅 GHA 缓存 — 否决（用户决策）：放弃本地↔CI 的产物复用与无上限缓存；用户将修复 Mac mini 网络，连通性不再是阻碍。

决策 6：Dependabot（而非 Renovate / 手动）

原生、零 App 装配，.github/dependabot.yml 一文件托管 actions(SHA)/gradle/pnpm，按周分组降噪。

备选 A：Renovate — 否决：SHA 管理更强但需装 GitHub App，对单人徒增装配。
备选 B：手动升级 — 否决：pin SHA 后不托管会滞后腐化。

决策 7：不上 Develocity Predictive Test Selection

PTS 是企业级「真正工业答案」，但需 ≥14 天历史 + 50+ 次执行冷启动、私有商业项目无免费层。单人 + 私有 + 无历史三条全不满足。

否决理由：当前阶段过度工程；服务级门控 + build cache 已覆盖收益。

风险与缓解

风险等级缓解
detect-changes 路由错误：该跑的服务没跑、漏测合并 high TDD 先覆盖六场景（单服务/foundation/仅portal/仅docs/混合/workflows 自身）；未识别路径保守全跑；.github/workflows/** 与 foundation 变更强制全跑
改名/删 workflow 导致 required-check 失配、PR 永久 pending high gate job 名严格保持 required-check；删 workflow 前确认 portal-ci-required-check 未进保护（已确认）；feature branch 实跑四场景验证后再合并
服务级门控漏测：未来新增跨服务测试时会被错跳 mid 文档化「零跨服务」不变量；nightly 全量兜底；新增跨服务测试时同步更新门控规则或单列 e2e 档
大 PR 评审负担重 mid 规格 + writing-plans 拆任务推进；如需可拆「①核心门控重构 / ②硬化」两个 PR
Mac mini cache node 不可达 low Gradle 远程缓存 fail-soft，退化为缓存未命中，GHA 缓存兜底，不阻断 CI
pin SHA 后 action 更新滞后腐化 low Dependabot 周更分组托管，CodeRabbit 不评 bot PR
