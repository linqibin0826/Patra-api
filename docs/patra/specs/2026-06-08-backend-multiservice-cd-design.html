后端多服务 CD 设计

📅 2026-06-08 🌿 worktree-cd-backend-multiservice 👤 Lin 🎯 spec draft
关键决策摘要

把 object-storage / catalog / ingest / gateway 四个后端服务接入已有的 Mac mini self-hosted CD（registry 已完成，作为模板）。采用单 workflow + 动态 matrix + 选择性构建：detect-changes 用 git diff 算出本次改动了哪些服务（含「改公共面 → 重建全部」的正确性规则）→ matrix 只并行构建改动的服务并推 GHCR → Mac mini 选择性 compose pull + up。5 个服务共用一份分层 Dockerfile与一个服务 SSOT（services.json），加新服务只改配置、不改工作流逻辑。

1. 背景与现状

registry 已通过 PR #137–142 完成容器化 + Spring Boot 4 分层 jar + 端到端 CD：merge main → 云端（ubuntu）build 镜像推 GHCR → Mac mini self-hosted runner 部署（auths 绕钥匙串 + 软链 compose 插件 + pull 重试 + health check）。现把其余 4 个后端服务纳入同一条流水线。

关键事实（已核查）：基建全部已 provision —— docker-compose.core.yaml 有 PG/Redis/Nacos，jobs.yaml 有 RocketMQ + xxl-job，storage.yaml 有 MinIO；5 个服务全部用同一 linqibin.hexagonal-boot 约定插件打包（bootJar archiveClassifier="" + 禁 plain jar），连 gateway（Spring Cloud Gateway / WebFlux）也是普通 fat jar，意味着刚做的分层 Dockerfile 是 5 个服务的通用模板。另发现 patra-object-storage 是完整的第 5 个服务（六层齐全），且 catalog / ingest 都通过 lb://patra-object-storage HTTP 依赖它 —— 是个隐藏的前置依赖。

2. 范围边界

In Scope
  • object-storage(6200) / catalog(6300) / ingest(6100) / gateway(9528) 四服务接入 CD
  • 服务 SSOT：patra-infra/cd/services.json
  • 共享分层 Dockerfile（合并删除 registry 那份）
  • cd.yml 重写：detect-changes（含「改公共面 → 重建全部」规则）+ matrix 选择性 build/push + 选择性 deploy
  • docker-compose.apps.yaml 扩为 5 服务
  • env 结构：.env.common + .env.{svc} + .env.{svc}.secret
  • workflow_dispatch 单服务部署 / 回滚到指定 tag
Out of Scope
  • 前端 patra-portal CD（结构不同，另开一轮 brainstorm）
  • gateway 功能加固（本轮只部署骨架，filter/限流/认证不在此）
  • 蓝绿 / 零停机部署（dev 环境 up -d 重建够用）
  • 多架构镜像（Mac mini 单 arm64 目标）
  • 新增基建服务（PG/Redis/Nacos/MinIO/RocketMQ/xxl-job 已全部 provision）

4. 工作流架构（方案 A：单 workflow + 动态 matrix + 选择性构建）

cd.yml 三段 job，触发 push:main（paths 扩到 patra-api 全部服务 + patra-infra/docker + cd.yml + 共享面）与 workflow_dispatch：

job 1 — detect-changes（ubuntu）

用 git diff --name-only 对比本次 push 的前后 commit，按 services.json 把改动路径映射成服务名，输出 services（JSON 数组）供下游 matrix。核心规则：

  • 改 patra-api/patra-{svc}/** 或 gateway 目录 → 该服务进 matrix
  • 改共享面（patra-common-* / linqibin-spring-boot-starter-* / build-logic/ / patra-infra/docker/service.Dockerfile / docker-compose.apps.yaml / .env.common）→ 输出全部 5 个服务（公共依赖变了，所有服务的 jar 都需重建重部）
  • workflow_dispatch → 输出指定的单个服务（或 all）
  • github.event.before 为全零（首次 / force push）时 → fallback 为全部服务

job 2 — build-and-push（ubuntu，matrix）

strategy.matrix.service: ${{ fromJson(needs.detect-changes.outputs.services) }}，只对改动的服务并行执行（一套 step 参数化）：setup-java 25 + gradle bootJar（matrix.service 对应的 gradleTask）→ docker build -f patra-infra/docker/service.Dockerfile {context} → 推 ghcr.io/linqibin0826/patra-{service}:{sha} + :latest。空 matrix（无服务改动）时整 job 跳过。

job 3 — deploy（self-hosted macmini，matrix）

沿用 registry 已验证的部署机制（auths 写 DOCKER_CONFIG/config.json 绕钥匙串 + 软链 cli-plugins + pull 重试）。对每个改动服务：export {SVC}_IMAGE_TAG={sha} → docker compose pull {service}（重试 3 次）→ compose up -d {service} → 轮询该服务端口的 /actuator/health 直到 UP。回滚（dispatch 指定 tag、build 跳过）时仍部署。

5. 共享 Dockerfile / compose / env

共享分层 Dockerfile — patra-infra/docker/service.Dockerfile

把 registry 那份分层 Dockerfile 泛化：内容逐字节通用（COPY build/libs/*.jar 本就与服务无关），唯一参数化点是端口 → ARG APP_PORT + EXPOSE ${APP_PORT}（EXPOSE 仅文档性，实际端口由 compose 映射）。保留多阶段 jarmode=tools extract --layers、非 root appuser、/app/logs 权限、curl、内存上限、瘦 jar entrypoint。删除 patra-registry-boot/Dockerfile。

docker-compose.apps.yaml 扩为 5 服务

每个服务一个 service 块：image: ghcr.io/linqibin0826/patra-{svc}:${{SVC}_IMAGE_TAG:-latest}、env_file: [.env.common, .env.{svc}, {path: .env.{svc}.secret, required: false}]、ports: {host}:{container}、healthcheck curl 各自端口 /actuator/health、networks: patra-net（external）。无 depends_on 链（见决策 5）。

env 结构

.env.common（共享基建坐标：NACOS_HOST/PORT、PG host、Redis、MinIO、RocketMQ namesrv、xxl-job admin —— dev 默认，进仓库）+ .env.{svc}（服务专属：DB 名、SPRING_PROFILES_ACTIVE、服务端口 —— dev 默认，进仓库）+ .env.{svc}.secret（真敏感密钥，.gitignore 已含 .env.*.secret，可选）。registry 现有 .env.apps 改名 .env.registry 以统一命名。

6. 关键决策与备选

决策 1：工作流采用方案 A（单 workflow + 动态 matrix + 选择性构建）

一个 cd.yml，detect-changes 算改动服务 → matrix 只构建改动的 → 选择性 deploy。DRY、只构建改动的、加服务只加配置、并行快。

备选 B（可复用 workflow workflow_call）：抽 cd-service.yml 逐服务 call — 否决：reusable 的 inputs/secrets 传递样板多，对 5 个同构服务是过度抽象，matrix 已够 DRY。
备选 C（每服务一个 workflow 文件）：5 份 cd-*.yml — 否决：5 份高度重复 YAML，改一处部署逻辑要同步 5 个文件，DRY 灾难，绿地项目不该如此。

决策 2：5 服务共用一份 Dockerfile，删除 registry 自己那份

5 个 Dockerfile 逐字节相同（仅端口可参数化）→ 抽成 patra-infra/docker/service.Dockerfile 一份，ARG APP_PORT 处理端口差异。

备选：每服务一份 Dockerfile（registry 模式复制 5 份）— 否决：DRY 违反，改部署镜像逻辑要同步 5 份，绿地无理由保留重复。

决策 3：detect-changes 纳入「改公共面 → 重建全部」规则

改 patra-common-* / starter / build-logic / 共享 Dockerfile / compose / .env.common 时，detect-changes 输出全部 5 个服务。

备选：只按 patra-{svc} 目录算改动 — 否决：公共模块改了却不重建依赖它的服务，是正确性 bug（服务跑着旧公共代码 / 旧依赖）。宁可多建不可漏建。

决策 4：env 用 common + svc + secret 三层

共享基建坐标抽 .env.common，服务专属各一份，密钥单独 gitignore。

备选：每服务一份自包含 env — 否决：基建坐标（Nacos/PG host 等）在 5 份里重复，改一处要同步 5 份。

决策 5：不做严格部署顺序（无 depends_on 链）

catalog/ingest 对 object-storage 是 lazy HTTP-Interface 调用（运行时才调，非启动时）+ Nacos 发现 + 重试 → 即使 object-storage 未起，它们也能 healthy 启动，仅运行时调用受影响。故选择性单服务部署安全。

备选：compose depends_on + 健康门控编排部署顺序 — 否决：启动健康不依赖下游，编排徒增复杂度；首次全量部署时建议同批 up 即可，无需强制链。

7. 风险与缓解

风险等级缓解
detect-changes 漏判共享面 → 服务跑旧公共依赖 mid 决策 3 的「改公共面 → 重建全部」规则覆盖；github.event.before 为空时 fallback 全建（宁可多建）
ingest 无 HTTP 业务端点，health check 依赖 actuator low ingest 是 Spring Boot 应用，actuator 独立于业务 Controller；落地时确认 /actuator/health 已暴露在服务端口
object-storage 未起时 catalog/ingest 运行时调用失败 low lazy HTTP + Nacos + 重试，仅运行时受影响、不影响启动健康；首次全量部署时同批 up
弱网首次拉 5 个镜像的依赖层（各约 80MB） mid 分层 jar 已优化：各服务 dependencies 层独立缓存，仅首次拉一次；pull 重试 3 次；后续部署只传变化的 application 层
gateway（WebFlux）与其他服务（MVC）同 compose low 独立容器、独立 fat jar，无同 classpath 冲突
matrix + 动态 fromJson YAML 出错（空 matrix / 语法） mid 空数组时下游 job 自动跳过（GitHub matrix 行为）；先用 workflow_dispatch 单服务跑通再依赖 push 自动触发
